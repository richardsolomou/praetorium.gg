# Hosted deployment

## Cloudflare

- Origin traffic must stay restricted to Cloudflare; the server trusts its visitor header for rate limits.
- Two rules live in the Cloudflare dashboard, not the repository. The HTML Cache Rule skips `better-auth.` cookies, `/_serverFn/`, and `/api/`, and its browser TTL must respect the origin. "Cache public reference API and images" lists public paths explicitly; never replace it with a blanket `/api/` rule, because photos, screenshots, private previews, and server functions must stay uncached.

## First administrator

Register and verify the operator account, then confirm its player ID from that account’s profile. From an operator connection to the auth SQLite database, bind that ID to `?1` in `UPDATE user SET role = 'admin' WHERE id = ?1 AND emailVerified = 1 AND NOT EXISTS (SELECT 1 FROM user WHERE role = 'admin') RETURNING id`. Verify that it returns the intended ID and sign in again. On an installation without mail delivery or a social sign-in provider, confirm control of the intended player account out of band and use the same query with the ID and empty-admin checks alone. An existing administrator can manage subsequent role changes in the app.

## Delivery

- `release.yml` releases each merge to `main`, or on dispatch, then `dokploy-web.yml` deploys it. Roll back by dispatching `dokploy-web.yml` with a `revision`; the next merge redeploys `main` unless Release is disabled.
- Production follows upstream catalogue sources in the release, not on the box: `dokploy-web.yml`'s live catalogue job refreshes from the published live archive (`catalogue/live/production.tar.gz` in the catalogue bucket) and publishes the result before replicas change, and a new replica starts from that archive, so its own refresh finds nothing to do. Only production deploys, including a dispatched rollback, pass `--publish`; pull request runs only prepare. An archive is used only by a checkout with the same `catalogue/` configuration, and a publish never replaces an archive that was refreshed from different sources since.
- Expiry of `GHCR_PULL_TOKEN` or `CHANGESETS_TOKEN` blocks deployment.
- Browser chunks import each other by stable names that each page's import map (`src/server/chunkImportMap.ts`) resolves to hashed files, so a release renames only the chunks whose code changed. A tab keeps the map it opened with, so never delete a published asset a recent release may still name.
- Browser tabs opened before a deploy decode a subscribed view's rows by the shape their bundle was built with, so add a new view rather than a column to one they subscribe to.
- Old and new versions coexist during a deploy: keep new module columns and result fields optional and appended, never remove or rename a result field until a release no longer reads it, and keep readers compatible while `scripts/migrateProductData.ts` backfills. The new server only takes traffic once its catalogue is built, minutes after the module lands, so the released server reads the new module all that time. `scripts/releasedServer.test.ts` runs the released server's preview seed, which reads back every procedure it can reach, against the module in memory; CI's unit lane points `RELEASED_CHECKOUT` at the revision production's `x-praetorium-revision` names, since a merge without a changeset deploys without a tag, and locally it runs with `RELEASED_CHECKOUT=<checkout of that revision> pnpm exec vitest run scripts/releasedServer.test.ts`. The same file fails when a procedure is neither read back by `scripts/seedPreview.ts` nor listed as unreachable, so a new read is covered from the next deploy on.
- Browser notifications run only while `WEB_PUSH_PUBLIC_KEY` (a variable) and `WEB_PUSH_PRIVATE_KEY` (a secret) hold a P-256 VAPID pair as unpadded base64url, as `npx web-push generate-vapid-keys` prints it, and `APP_URL` is set. Every browser subscription belongs to that pair: replacing it stops browser notifications until each player turns them on again.
- The module's `AUTH_ISSUER`, `AUTH_AUDIENCE`, and `OPERATOR_IDENTITY` are stored SpacetimeDB environment values that publishes do not send; change them with `spacetime env`.
- `scripts/nodeServer.ts` must stop within Docker's ten-second grace period.
- Production runs one web replica, which holds the auth SQLite on its `/data` volume, so a replacement is an outage until the new one is ready. `ensureWebHealthCheck` therefore replaces it only after about three minutes of missed probes, and `src/server/publicPageLoad.ts` answers signed-out page renders past its limit with a 503, so a crawler burst slows the site instead of stopping it. Each deploy applies the health check before updating the service.
- `/whats-new` reads `CHANGELOG.md`, which each release cuts to the releases it lists, moving older ones into `changelog/<month>.md`; correct or remove an entry by editing it.
- Rotating `DISCORD_ANNOUNCEMENTS_WEBHOOK_URL` must keep the R2 receipts; inspect pending deliveries before retrying an announcement.

## CI runners

- Every job runs on GitHub-hosted runners except some browser-test runners of the owner's own pull requests, which run on the owner's desktop: repository runners labelled `self-hosted`, `linux`, `desktop`, that only connect out to GitHub. The account runs 20 hosted jobs at once, so this keeps a pull request's other jobs from queueing.
- The `runs-on` expression in `ci-e2e.yml` routes only a `pull_request` event from a branch of this repository, opened by `richardsolomou`, to the desktop, since those jobs hold the R2 read keys. Dependabot, other authors, and every release, deploy, scheduled or dispatched job stay hosted, so production never waits on the desktop. A fork's pull request runs its own copy of the workflows and could name the desktop's labels itself, so the barrier for forks is the repository's fork approval policy (`all_external_contributors`): approving a fork's run lets its code onto the desktop, though without secrets.
- Those jobs go to the desktop only while `DESKTOP_RUNNER` is `on` and the desktop's heartbeat is fresh: runners 2 onwards, as many as the variable `DESKTOP_RUNNER_SLOTS` says (default 2, at most one fewer than the runners planned, so runner 1 stays hosted), each with 40% of a hosted runner's share of the tests, since downloading its caches over the home line adds about four minutes. A timer on the desktop stamps `DESKTOP_RUNNER_HEARTBEAT` with the Unix time every two minutes while every desktop runner is up and the machine has room for them, and the browser-test build counts a stamp older than three minutes, or none, as the desktop being away, so a run planned then stays hosted. A desktop that drops mid-run fails its jobs: re-run all jobs to plan around it, or set `gh variable set DESKTOP_RUNNER --body off` first when re-running only the failed ones.
- The desktop's `gha-heartbeat.timer` stamps `DESKTOP_RUNNER_HEARTBEAT` every two minutes while every enabled runner is up and at least one is idle, with about 5 GB free per idle runner and load under 16 plus 4 per busy runner. It uses a fine-grained token limited to this repository with only Variables read and write, kept root-only in `/etc/gha-heartbeat/token`. To rotate it, create the replacement, write it to that file with mode 600, and revoke the old token once the variable moves again.
- The runners run as a dedicated user in systemd services with a capped memory share and a CPU share no larger than interactive work, with the owner's files and the Windows host out of reach, and each job starts with an empty `/tmp`. Browser-test ports are chosen free per stack, so two pull requests' runners can share the machine.
- Each desktop runner holds about 5 GB, and the desktop's other work can still exhaust its memory; a runner whose job failed with `The runner has received a shutdown signal` was killed for memory, so re-run it.

## Pull request previews

- Previews run at `pr-<number>.praetorium.gg`; ready means `/api/health` reports the expected commit. A preview deploys only when a maintainer adds the `preview` label (`gh pr edit <number> --add-label preview`), so pushes do not crowd production on hera; the build takes the label off, so adding it again deploys the newest commit, and the preview comment names the commit it shows. A fork's preview also waits for approval in the `pr-preview` environment, because the fork's own copy of the image workflow decides when it builds, and keeps its label, so remove it before adding it again.
- Previews are public and share one runtime catalogue cache; keep sensitive data out. Redeploying resets their data.
- A preview starts from the snapshot its commit pins, as CI tests it, and downloads the server projections and browser downloads its pull request's CI build published for that snapshot and compiler, instead of building a catalogue from sources; it builds them itself only when its compiler differs from the merge ref's. It never follows upstream sources after that, so it shows the catalogue its pull request ships and rebuilds nothing on hera. It holds only `SNAPSHOT_R2_*`, the read-only key for the catalogue bucket, because preview code is unreviewed and must never reach the backups or players' photos that `PRIVATE_R2_*` opens. Photo and screenshot storage therefore stays off in previews.
- Previews share hera with production, so each is capped at 3 GiB, with a 2 GiB Node heap, and at most two run beside production's peak: deploying another stops the one first deployed longest ago until its next deploy.
- A server holds about 1.3 GiB of live heap once ready, every rules version loaded, so a smaller heap cannot start. `scripts/measureServingMemory.ts` starts a built server as a preview does, from a snapshot with the preview seed, and reports its live heap at readiness and after each kind of reference page, with `--budget` to fail over a limit; run it on main and the branch before changing what the server keeps.
- Sign in with `preview@praetorium.gg` / `preview-preview-preview` or `opponent@praetorium.gg` / `opponent-opponent-opponent`.

## Backups

- Copying the running product database freezes it: resume before upload, and never scale the database down or pull helper images while frozen.
- The production web server checks the published backup hourly and logs an error, which fires the "Server error logs" alert, once it is more than 13 hours old.

### Restore

- The product database backs up every six hours through `scripts/spacetime-backup.timer`, which runs `scripts/backupSpacetime.py` and retains every snapshot for two days, the newest snapshot per UTC day until fourteen days old, and the newest per UTC week (Monday start) until six weeks old, across `.tar` and `.tar.gz` archives. Archives use `gzip -1` after the database resumes. Nothing deploys them: `scripts/installSpacetimeBackup.sh <host> install [config.json]` installs both from the checkout, and `scripts/installSpacetimeBackup.sh <host> check` compares a host read-only, so run it after changing either. Deploy the readback script accepting `.tar.gz` before installing the backup writer. The config holds the R2 credentials and stays out of Git; pass it on a new host only.
- `<prefix>/backups/latest.json` in the private bucket names the newest data and identity archive and their sha256; restore only a pair that matches it. Extract the data archive with `--strip-components=2` into the new data volume, the identity archive into the identity volume, and delete `spacetime.pid`. Start the same image production's Dokploy app runs (`scripts/verifySpacetimeBackup.sh` reads it from Dokploy; it is pinned separately from the CLI and SDK), with `--jwt-priv-key-path` and `--jwt-pub-key-path` pointing at the restored identity keys. Those keys keep the owner and operator tokens valid, so never generate new ones.
- The auth SQLite and `AUTH_SECRET` back up hourly through the Dokploy schedule `scripts/dokployAuthSchedule.ts` creates on each production deploy, as `backups/auth/production/<stamp>-<id>.zip` in the private bucket. Each run keeps every archive from the last 48 hours, the newest of each UTC day for 30 days and the newest of each week after that, and never prunes one at or after the newest product backup. An auth archive must be at or after the product backup's `createdAt`, so every account a restored row names exists: `backups/auth/production/latest.json` always is, and `node scripts/nodeAuthBackup.ts restore latest <new directory>` verifies and unpacks it; for an older product backup, pass the first key at or after it instead of `latest`. Put `auth.sqlite` on the web `/data` volume before the web service starts, and set `AUTH_SECRET` to the contents of `auth-secret`. Once the product database is up, run `pnpm exec tsx scripts/replayAuthDeletions.ts <new directory>/auth.sqlite <createdAt>` with its `SPACETIME_URL`, `SPACETIME_DATABASE` and `SPACETIME_OPERATOR_TOKEN`: it deletes again the data of every account deleted after the product backup, which the backup still holds.
- Auth archive retention belongs to the backup job: do not apply R2 lifecycle expiration to `backups/auth/production/`, because an age cutoff deletes the weekly recovery points and can remove the archive paired with the newest product backup. Keep the bucket's multipart-upload abort rule; it does not expire completed backups.
- Rehearsed on 2026-11-16 with a 2.4 GB data archive: download and checksum 31 s on the host, extraction 13 s, start and replay under 5 s.
