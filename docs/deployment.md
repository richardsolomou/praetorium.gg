# Hosted deployment

[praetorium.gg](https://praetorium.gg) is the supported service. The source is available for inspection and contribution. [Running locally](development/running-locally.md) describes the development environment; this repository does not maintain a self-hosted service configuration.

The hosted web application runs on Dokploy. SQLite holds accounts and sessions on a volume shared by the production web replicas. SpacetimeDB holds rosters, battles, leagues, and realtime updates. The public `praetorium` R2 bucket serves profile images and catalogue data at `s3.praetorium.gg`. The private `praetorium-private` R2 bucket holds off-host backups and the combat-rule audit cache. Each pull request preview has separate account and product databases; see [Pull request previews](development/pr-previews.md).

The release workflow builds one digest-pinned Node image after changes reach `main`, publishes the SpacetimeDB module without replacing its database, and deploys that image to Dokploy. Its release candidate pull request adds only the version and changelog, so when `main` is the exact tree a passing CI run recorded for the pull request that produced it, the candidate skips CI; `scripts/releaseProof.sh` decides this, and any doubt runs every job. GitHub builds the image; Dokploy pulls it without rebuilding. Before changing replicas or publishing the product module, the workflow copies hashed assets from both the installed digest-pinned image and its replacement to `web-assets/` in the public R2 bucket. It verifies bytes and immutable cache headers through storage and the public CDN, then routes same-origin `/assets/` reads directly to that shared store through Traefik. The route is verified on the hosted domain and restored to its previous configuration if verification fails. Traefik sends asset errors through the application's uncached asset-miss handler. Retained assets are not deleted during releases, so an older open tab can still load its lazy chunks after the rollout or a rollback. Source maps are excluded. Staging uses the same deployment workflow with separate data. The [pull request preview workflow](development/pr-previews.md) creates isolated disposable data for each pull request.

Before publishing an existing SpacetimeDB module, the workflow obtains its migration plan and token. Automatic migrations may disconnect existing clients when the schema changes; manual migrations stop the deployment without clearing data.

The source-snapshot publisher resolves community data separately from the application, verifies each archive after upload, and updates the current pointer only after the archive is readable. Releases package a pinned, verified snapshot, so publishing a new snapshot does not change a running application's rules data.

After a production deploy, `scripts/submitIndexNow.ts` waits until every replica reports the new revision, compares the sitemap with the copy recorded before the deploy, and submits the pages it added or dated afresh to IndexNow. The `INDEXNOW_KEY` secret is passed only to production, which serves it at `/indexnow.txt`; without it the key file is a `404` and nothing is submitted. A failed submission does not fail the release.

The edge in front of the Node server rewrites `x-forwarded-for` to its own address, while Cloudflare names the visitor in `cf-connecting-ip`. `scripts/nodeServer.ts` puts that address first, because PostHog through the ingest proxy, the reference rate limit and the crawler log all read the first `x-forwarded-for` entry. A request that reaches the origin without passing through Cloudflare can choose that header, so the origin should accept traffic only from Cloudflare.

Each web replica reads the packaged catalogue from its image and prepares it in memory. Production SQLite backups include the matching auth secret, are verified by restoring an off-host archive, and expire from R2 after 30 days. The product database has its own off-host backup and restore check. Both web replicas and SpacetimeDB run on one VM, so a VM outage still interrupts the service until it is restored.

SpacetimeDB backups preserve connections by briefly freezing the database process while copying its data and identity volumes together. The copy has a five-second budget and an independent ten-second resume watchdog. Uploads and checksum readback run after the process resumes; a manifest identifies the verified archive pair. The schedule runs every six hours and retains 56 archives of each volume. The restore check rejects a manifest older than 12 hours. Backups do not scale the database down or pull a helper image while it is frozen.

The public Node proxy owns a separate Nitro child process. On `SIGTERM` or `SIGINT`, it stops accepting connections, closes upgraded connections, and gives active HTTP requests up to five seconds to complete before stopping Nitro. Nitro then has three seconds to exit before a forced stop, within the hosted service's ten-second Docker stop grace period. The readiness gate waits for the child's `/api/health` before opening the public listener; the existing start-first rolling deployment and health check remain in place.

Open pages check an uncached `/api/release` endpoint once a minute while visible and when focus returns. A newer semantic version shows a release notice with Refresh and Later actions. Refresh is explicit so a deployment does not discard unsaved edits; Later hides that version until the tab reloads or another release appears.
