# Hosted deployment

[praetorium.gg](https://praetorium.gg) is the supported service; the repository maintains no self-hosted service configuration. [Running locally](development/running-locally.md) and [Mobile release](development/mobile-release.md) own their own paths.

## Runtime

Dokploy runs the web replicas, with SQLite accounts/sessions and the runtime catalogue cache on a shared volume and SpacetimeDB for product state. Public R2 stores profile images, application assets and optional compiled catalogue caches; private R2 stores catalogue snapshots, backups, the audit cache, feedback screenshots and collection photos. The replicas and product database share one VM, so an outage requires restoration.

The Node server trusts Cloudflare's visitor header for proxying and rate limits, so restrict origin traffic to Cloudflare: direct callers could otherwise choose that header. Asset errors use `no-store` so a missing file cannot poison the browser or edge cache.

Signed-out reference pages carry a 20-second `s-maxage` (`src/server/sharedPageCache.ts`), below the browser's 30-second query staleness so hydrated data needs no refetch; pages that read cookies while rendering and signed-in responses send none. A Cloudflare Cache Rule on the `praetorium.gg` host, configured outside the repository, makes HTML cacheable except requests carrying a `better-auth.` cookie or under `/_serverFn/` and `/api/`. Its edge TTL uses the origin's `Cache-Control` and bypasses when it is absent; its browser TTL respects the origin, because the zone's four-hour Browser Cache TTL would otherwise raise `max-age=0`. Nothing purges the edge after a deploy, so for up to 20 seconds a cached page can reference removed assets.

The separate “Cache public reference API and images” Cloudflare rule allows only GET/HEAD requests on `praetorium.gg` for `/api/reference/v1` and its children, `/api/faction-icons/`, `/api/previews/site`, datasheet and detachment previews, `/guides/*.png`, `/logo.svg`, and `/favicon.svg`. It follows origin cache headers, bypasses responses without them, respects the origin's browser TTL, and uses raw request-header values for `Vary` so the reference API's JSON and Markdown representations remain separate. Keep query strings in the cache key. Collection photos, feedback screenshots, player/roster/battle previews, and server functions stay outside this rule; do not replace it with a blanket `/api/` cache rule.

`cacheAssetResponse` in `scripts/nodeServer.ts` gives guide PNGs with a content hash in their filename a year of immutable caching, and the unversioned logo and favicon one day. It preserves explicit upstream cache policies and responses that set cookies, and marks missing or failed image/build assets `no-store`. `e2e/caching.spec.ts` checks the served headers and conditional reads. After changing an edge rule, verify repeated production GETs reach `CF-Cache-Status: HIT`, alternate JSON and Markdown requests at the same URL, and confirm inaccessible photos and missing assets remain uncached.

## Delivery

`.github/workflows/dokploy-web.yml` owns image publication, product migration, deployment, and health checks, deploying a digest-pinned image without rebuilding it. Staging uses separate data. Images are private in GHCR; Dokploy pulls production and preview images with the `GHCR_PULL_TOKEN` repository secret, a classic token with only `read:packages`, so production and previews stop deploying if it expires.

`.github/workflows/release.yml` runs on every push to `main`: with pending changesets it commits a `[skip ci]` release commit directly on `main`, tags it, creates the GitHub Release, and deploys it; otherwise it deploys the pushed commit. [Mobile release](development/mobile-release.md#build-and-upload) owns whether a release rebuilds the app. The release push uses the `CHANGESETS_TOKEN` repository secret, a fine-grained owner token that the `main` ruleset's admin bypass lets past required checks; if it expires or loses access, production is not deployed until the secret is replaced. A release deploy refuses a revision that does not contain the one production runs (the installed image's `sha-` tag), so re-running an older release cannot roll back; roll back explicitly through `dokploy-web.yml`'s `workflow_dispatch` with a `revision`.

`Dockerfile.node` builds the application once, so the `amd64` and `arm64` variants carry identical hashed application assets and product module. It carries no fetched catalogue data. Startup prepares source data, server projections and browser downloads in the persistent catalogue cache; the background worker refreshes that data from configured branches without rebuilding or restarting the image. [Catalogue data](development/catalogue-data.md#runtime-updates) owns validation, atomic activation and retention. Nitro copies the build platform's native `libsql` binary, so the image replaces it with the target platform's and fails if it cannot load. Sharp resolves from the target platform's production dependencies rather than Nitro's traced build-platform copy; the image build verifies an actual WebP encode. The image must contain `server/combat-calculation-worker.mjs` ([Combat simulation](development/combat-simulation.md)). It ships no curl or wget; health check commands, including the one `scripts/configureDokployNode.ts` saves, run `node /app/scripts/healthcheck.ts`.

Each deploy keeps old and new versions compatible:

- First, `scripts/publishWebAssets.ts` copies hashed assets from the installed and replacement images to public R2 and routes `/assets/` reads there, so older open tabs and rollbacks keep working.
- Product publication requires a migration plan/token. Automatic schema migrations may disconnect clients; manual migrations stop delivery without clearing data.
- The module reads its auth issuer, audience, and operator identity from required SpacetimeDB environment values (`AUTH_ISSUER`, `AUTH_AUDIENCE`, `OPERATOR_IDENTITY`). Publishes keep stored values, so `dokploy-web.yml` sends none; a database without them refuses the publish and keeps its installed module. Previews and local stacks send them as `spacetime-environment` headers (`scripts/lib/spacetimeEnvironment.ts`). Change a stored value with `spacetime env` or `PATCH /v1/database/<name>/environment`.
- The product module is published before replicas change, so the previous web build reads rows with columns it does not know. `src/server/spacetimeOperator.ts` parses module results with non-strict schemas that drop unknown fields; keep new columns and result fields optional and appended.
- Between module publication and the replica update, `scripts/migrateProductData.ts` upgrades saved rows in atomic, rerunnable batches; failure stops delivery. Keep product readers compatible during the backfill, and remove historical-row branches only after verifying the live database upgrade. Web-only rollbacks reuse the installed module and skip the migration.
- Application assets stay pinned to the image. Catalogue data and its browser downloads advance together through the runtime updater, retaining the last complete revision on failure.

The start period in `scripts/configureDokployNode.ts` covers the first catalogue download and compilation as well as application readiness. Cached startups can serve their retained catalogue while the updater checks for changes. That proxy opens its public listener only after the Nitro child is healthy; its readiness requests share one deadline and the shutdown signal rather than short per-request timeouts, and its shutdown must finish within Docker's ten-second stop grace period. [Catalogue data](development/catalogue-data.md#sources-and-loading) owns runtime loading and memory.

The offline reference and app manifests (`offline-reference-version.json`, `offline-app-version.json`) are uncached and point to retained hashed assets. The reference and construction downloads are gzip data served as `application/octet-stream` without HTTP content encoding, so the client decompresses it consistently through Nitro and the CDN. Keep generated bundles and copied rules out of Git.

Open pages poll the uncached `/api/release` and offer a manual Refresh for a newer version. `/whats-new` reads `CHANGELOG.md`, so changeset summaries are player-facing copy. `INDEXNOW_KEY` is production-only; IndexNow submission failure does not fail the release. Its before/after sitemap reads use separate revision-specific query strings to avoid the shared sitemap's one-hour edge cache. The release retains both XML responses for seven days in the `production-sitemaps` artifact, including on submission failure. `TYPESAFE_API_KEY` is production-only too, so only real uploads are screened.

## Pull request previews

Pull requests receive disposable Dokploy previews at `pr-<number>.praetorium.gg`; the PR's status comment links readiness and failures. Ready means `/api/health` reports the expected commit, not merely that a container started. After the preview CLI reaches its health deadline, deployment allows up to 30 more minutes for initial catalogue preparation; an older healthy revision cannot satisfy readiness.

`.github/workflows/dokploy-preview-image.yml` builds a digest-pinned image without deployment credentials; the trusted `dokploy-preview-deploy.yml` job and `scripts/dokployPreview.ts` deploy it. Fork artifacts require maintainer approval before trusted deployment.

Preview images target `linux/arm64`, matching the hosted VM. The shared build workflow applies the same target to registry images and fork artifacts. Deployment runs on `ubuntu-24.04-arm` so the trusted lifecycle script can pull the image and extract its database module natively.

Each preview has its own SQLite accounts, SpacetimeDB database, secret, operator identity, auth issuer, audience, and runtime catalogue cache. Redeployment resets both stores and ends old sessions; deterministic seed IDs retain cross-store links. Sign in with `preview@praetorium.gg` / `preview-preview-preview` or `opponent@praetorium.gg` / `opponent-opponent-opponent`. Previews are public; keep sensitive data out. Closing or merging removes preview resources, and scheduled pruning recovers missed cleanup.

## Backups

Auth backups include the matching secret and are checked by restoring an off-host archive. Product backups preserve data and identity volumes together. `scripts/spacetime-backup.service`, `scripts/spacetime-backup.timer`, and the backup scripts own scheduling/retention; `backup-readback.yml` owns verification.

Copying the running product database uses a bounded freeze with an independent resume watchdog. Resume before upload/readback. Verify archive checksums, paired-volume manifest, and freshness on restore. Do not scale the database down or pull helper images while frozen. A backup command succeeding does not prove restoration.
