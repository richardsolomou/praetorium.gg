# Hosted deployment

[praetorium.gg](https://praetorium.gg) is the supported service. [Running locally](development/running-locally.md) covers contribution; the repository maintains no self-hosted service configuration. [PR previews](development/pr-previews.md) and [Mobile release](development/mobile-release.md) own their delivery paths.

## Runtime

Dokploy runs the web replicas. SQLite accounts/sessions share a production volume; SpacetimeDB owns product state and realtime updates. Public R2 stores profile images/catalogues; private R2 stores backups/audit cache. The replicas and product database share one VM, so an outage requires restoration.

The Node server trusts Cloudflare's visitor header for proxying/rate limits. Restrict origin traffic to Cloudflare: direct callers could otherwise choose that header. Asset errors use `no-store` so a missing file cannot poison the browser or edge cache.

## Delivery

Combat estimates use two worker threads per web replica, separate from the request event loop. Each worker has a 128 MiB old-generation heap limit; the pool bounds queued and running pairs and caches answers in memory per replica. `vite.seed.config.ts` builds the Node calculation worker alongside the preview seed entry, and the production image must contain `server/combat-calculation-worker.mjs` in its output directory. The offline browser worker remains in the saved application bundle. [Combat simulation](development/combat-simulation.md) owns calculation limits and cache behavior.

`.github/workflows/dokploy-web.yml` owns image publication, product migration, Dokploy deployment, and health checks. It deploys a digest-pinned image without rebuilding it. Production follows main/releases; staging uses separate data.

The production image is published for `linux/amd64` and `linux/arm64`. `Dockerfile.node` builds the application once on the runner's own platform, so every variant carries identical hashed assets and product module; only the production dependencies install per architecture, under emulation for arm64. Nitro's server output copies the build platform's native `libsql` binary, so the image replaces it with the target platform's from that install and fails the build if `libsql` cannot load. Hosts that accept only a plain health check command use `node scripts/healthcheck.ts`, because the image ships no curl or wget.

`.github/workflows/release.yml` runs on every push to `main`. With pending changesets, it commits the version and changelog updates as `chore: release vX [skip ci]` directly on `main`, tags that commit, creates the GitHub Release, and deploys it to production; without them it deploys the pushed commit. The release commit changes only release metadata on the tree CI already tested, so it gets no CI run of its own, and `[skip ci]` also skips the other push workflows for it. The release run dispatches the coverage baseline after versioning and checks whether native inputs changed before dispatching iOS delivery; web-only releases do not rebuild the mobile app. [Mobile release](development/mobile-release.md#build-and-upload) owns the native input check and delivery baseline. The push uses the `CHANGESETS_TOKEN` repository secret, a fine-grained token acting as the owner, which the `main` ruleset's admin bypass lets past required checks. If that token expires or loses access, the release push is rejected and production is not deployed until the secret is replaced.

Before changing replicas or publishing the product module, the workflow copies hashed assets from the installed and replacement images to `web-assets/` in public R2. It verifies their bytes and immutable cache headers through storage and the public CDN, then routes same-origin `/assets/` reads directly to that store through Traefik. Hosted route verification restores the previous configuration on failure. Asset errors use the application's uncached miss handler. Source maps are excluded; retained files remain available to older open tabs and rollbacks.

The client build generates the public offline reference from the same catalogue projections as hosted reads. `offline-reference-version.json` and `offline-app-version.json` are uncached manifests pointing to retained hashed assets. Reference versions depend only on reference content; application versions cover both JavaScript and CSS. The reference is gzip data in a `.bin` asset, served as `application/octet-stream` without HTTP content encoding so the client decompresses it consistently through Nitro and the CDN. Construction sources share unchanged base data in the saved bundle and reconstruct a selected edition on demand, within the existing size limit. Terrain geometry lives in reference queries rather than repeated construction sources. Generation requires the pinned catalogue and fails on incomplete data or asset limits. Keep generated bundles and copied rules out of Git.

The public Node proxy owns a separate Nitro child process. Shutdown stops accepting connections, closes upgraded connections, and drains HTTP requests for up to five seconds before stopping Nitro. The child then has three seconds to exit, within Docker's ten-second stop grace period. The public listener opens only after the child's `/api/health` succeeds.

Deployment configuration gives a new replica six minutes to warm its pinned catalogue and retained rules before failed health checks count toward rollback. Checks still run every ten seconds and admit traffic as soon as readiness succeeds. After startup, three failed checks mark the replica unhealthy. Keep this allowance at least as long as the Node proxy's bounded readiness loop; retained rules can exceed a minute on the production VM.

The image build restores the compiled catalogue runtime for its key from the shared store on the catalogue mirror, or compiles it from the pinned snapshot when no build has shared it yet, alongside the Nitro server and the offline bundle built from the same snapshot. Readiness loads those projections and the base construction catalogue before accepting traffic; every rules version and faction construction index is then built in the background, between requests. Edition contexts stay cached for the process lifetime to avoid request-time reloads. [Catalogue data](development/catalogue-data.md#sources-and-loading) owns runtime validation and memory benchmarking.

The Node proxy's readiness requests share one six-minute deadline and its shutdown signal. Let an in-flight request wait for catalogue warmup instead of cancelling it on a short per-request timeout. Verify delayed readiness and shutdown while a probe is pending in `scripts/nodeServer.integration.test.ts`.

Open pages check an uncached `/api/release` endpoint once a minute while visible and when focus returns. A newer web version offers a manual Refresh action, including inside the native WebView. After a refresh, a one-line What's new notice lists changes since the version this browser last acknowledged; dismissing it or opening `/whats-new` records the current version in local storage, and a first visit records it without a notice. The notice and page read `CHANGELOG.md`, so changeset summaries are player-facing copy. Battle trackers and the roster builder do not show the notice. `/reference-worker.js` is uncached so browsers receive the current navigation behavior after deployment. When introducing this header, purge that URL from the edge cache after deployment to remove previously cached responses. Native shell updates use compatible over-the-air updates and app-store builds; [Mobile release](development/mobile-release.md) owns compatibility and delivery.

Product publication requires a migration plan/token. Automatic schema migrations may disconnect clients; manual migrations stop delivery without clearing data. The product module is published before replicas change, so the previous web build reads rows with columns it does not know: `src/server/spacetimeOperator.ts` parses whole table rows with non-strict schemas that drop unknown columns. Keep new columns optional and appended. Catalogue assets are pinned and verified inside the image; publishing a source snapshot alone does not update the running service.

After publishing the module and before updating web replicas, `scripts/migrateProductData.ts` inventories saved product keys and upgrades rows through the operator-only `migrate_product_data` procedure. Local startup runs the same migration after configuring its module. Batches contain at most 20 keys, commit atomically, retain roster timestamps and sync receipts, and can be rerun after a partial failure. Inventories and requests have size, count and time limits; failure stops delivery. Current writes normalize historical roster fields so delayed devices cannot recreate them. Keep product readers compatible during publication and backfill; remove their historical-row branches only after verifying the live database upgrade. New web readers require migrated roster metadata. Web-only rollbacks reuse the installed product module and skip the migration.

After production deployment, `scripts/submitIndexNow.ts` waits for every replica's revision and submits measured sitemap additions/changes. `INDEXNOW_KEY` is production-only; missing keys disable submission, and submission failure does not fail the release.

## Backups

Auth backups include the matching secret and are checked by restoring an off-host archive. Product backups preserve data and identity volumes together. `scripts/spacetime-backup.service`, `scripts/spacetime-backup.timer`, and the backup scripts own scheduling/retention; `backup-readback.yml` owns verification.

Copying the running product database uses a bounded freeze with an independent resume watchdog. Resume before upload/readback. Verify archive checksums, paired-volume manifest, and freshness on restore. Do not scale the database down or pull helper images while frozen. A backup command succeeding does not prove restoration.
