# Catalogue data: Collection

## Collection

A collection never changes pricing or legality. Counts are per datasheet ID (`src/core/collection.ts`), so a shared kit or alternative build is not modelled and roster units of one datasheet draw on the same count. Each entry holds at least one model; removal deletes the count, with its built and painted counts, in the same transaction. Painted models are built and built models are owned: `boundedProgress` lowers the bounded counts whenever a lower one changes, rather than refusing an edit another device may have made stale. Wishes (`collection_wish`) are wanted models apart from ownership and survive removal of the owned entry. Favourites are separate and say nothing about ownership. Keep read compatibility for pre-favourite heart rows until the data migration's backfill is verified. Battle-based suggestions must never block the page. Edits save to the durable queue before projecting; account downloads pass retention checks so an older download cannot overwrite a newer edit. `ModelCounter` keeps its latest local draft until its save is reflected in the incoming count so earlier saved values cannot reverse rapid steps; verify both directions, the persisted counts, and reload. The compact Max actions beside Built and Painted use that same counter save path, setting Built to Owned or Painted to Built without changing the other count. `collection_profile` checks publication and ownership in the same transaction as the read; [Product design](../../product-design.md) owns visibility. Cover changes in `e2e/collection.spec.ts`.

`src/core/collectionCsv.ts` owns the CSV format: a header row naming `datasheet` or `datasheet_id`, matching by ID before name and faction, and spreadsheet-formula escaping on export. Import is online only (`import_collection`): it reviews every row before saving, adds what is missing, treats a zero as leaving a saved count alone, never removes anything, and changes differing saved counts only when the player asks. `rosterReadiness` (`src/core/collectionReadiness.ts`) compares a roster with the reader's own collection in the builder's collapsed Your collection section. Wishlist suggestions (`src/core/wishlistSuggestions.ts`) read other players' recent public rosters through roster discovery, so a roster appears only with its owner's consent, Return the full candidate pool so filtering owned datasheets and wishes does not leave empty suggestion slots. The wishlist filters out owned datasheets and existing wishes using the current collection state, including unsynced edits; players can still manually wish for more models of a datasheet they own. Faction totals sum the current owned, built and painted counts, bounding progress through `boundedProgress` while edits sync. The collection's From your battles shelf (`fieldedDatasheets`) skips armies whose every roster is archived (`src/core/archivedArmies.ts`).

Collection photos live in the private bucket as `collection-photos/<uuid>`, up to `MAX_DATASHEET_PHOTOS` per collection row in `collection_photo`, found by its `collection_photo_row` index. The browser re-encodes uploads, which drops location metadata. The server uses sharp to decode JPEG, PNG and WebP and store a WebP preview, at most 320 pixels on its longest side, beside the original as `collection-photos/<uuid>.thumbnail.webp`. Registering a photo requires both objects, and a refused upload cleans up both. `/api/collection-photos/<uuid>` (`src/server/collectionPhotos.ts`) asks `collection_photo` for visibility on every read, including conditional requests. Successful responses use `private, no-cache` and an ETag from the immutable photo UUID: browsers retain the bytes but must revalidate access before reuse; an authorized match returns `304` without reading the bucket. Hiding, removal and account deletion still take effect on the next read, and errors remain `no-store`. Every path that drops a photo row records its id in `collection_photo_deletion` in the same transaction; the web sweep removes both objects before acknowledging deletion. Cards and galleries request `?size=thumbnail`, with a separate ETag; the viewer and direct links keep the original. The collection loader preloads photo IDs so cards can request their previews with the page.

At startup, photo maintenance pages through all photo IDs, including private and held photos, and creates missing thumbnails. Completed objects are skipped on rerun; failures are logged and retried on the ten-minute maintenance interval. A missing thumbnail is also generated on an authorized read. Generation checks that the photo still exists after writing, removing a preview if deletion raced the backfill. Generation never rewrites the original.

Likes are `collection_photo_like` rows counted into `collection_photo.likes` in the same transaction; `rankCollectionPhotos` in `src/core/collectionPhotos.ts` owns gallery order. Reports and review use `collection_photo.review` (`/admin?tab=photos`, `admin_collection_photos`); [Product design](../../product-design.md#watching-a-battle) owns who sees a reported photo. Administrators read any photo through the same route. With `TYPESAFE_API_KEY`, `src/server/photoScreening.ts` asks TypeSafe Jev whether each JPEG or PNG upload shows miniatures or content that does not belong, after it is stored ([Telemetry](../telemetry.md) owns how to read the results). Profile pictures get the same treatment with questions only for seriously inappropriate content. Jev images are an experimental TypeSafe feature, so the request format can change between its releases. Browsers upload collection photos and profile pictures as JPEG of at least 280 pixels a side, because Jev reads only JPEG and PNG of that size. Datasheet galleries read in the browser only, because signed-out reference HTML is shared-cached. Uploads are never queued; previews have no private bucket and refuse them.

`collection_stock` is retired but stays in the schema and account deletion until emptied, because SpacetimeDB refuses to drop a table with rows.
