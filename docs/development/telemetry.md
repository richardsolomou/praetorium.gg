# Telemetry

Praetorium uses PostHog for analytics, replay, flags, errors, performance, structured logs, metrics, and distributed traces. The integration is optional. Every product path works without PostHog variables. Browsers send events to the same-origin `/t` proxy, which forwards the visitor's address in `X-Forwarded-For` and drops cookies. `VITE_POSTHOG_HOST` must therefore name PostHog's ingestion host, such as `https://us.i.posthog.com`, rather than a managed reverse proxy: a managed proxy ignores that header and records the server's address instead.

Web Analytics uses the browser's pageviews. Most crawlers and AI agents run no JavaScript, so the server also records each `GET` or `HEAD` of a public reference page, `sitemap.xml`, `robots.txt`, `llms.txt`, or the reference API as a `$http_log` event, which PostHog's bot detection classifies by user agent. `src/server/crawlerRequests.ts` allows only paths that cannot name a player, battle, league, invitation or saved list. The event carries the path without its query string, the user agent, the referrer's origin, the method and the status. It sends no address, disables GeoIP, and creates no person profile. Its distinct id hashes the day, address and user agent under a salt that lives only in the process, so it counts clients within a day without linking them across days or restarts. A browser that runs JavaScript also sends its own `$pageview`, so human reads appear under both events. The public MCP reference uses the pinned `@posthog/mcp` SDK in production with the existing project token and host. MCP Analytics keeps tool names, timings, outcomes, protocol version, and anonymous sessions. It drops arguments, results, agent intent, client identifiers, and MCP exception events before capture. PostHog ingestion adds the server's address even when the SDK sets `$ip` to null, so the project's `Remove MCP Analytics IP` transformation clears `$ip` before storage for events with `$mcp_source = posthog_mcp_analytics`. The SDK does not change tool schemas or responses. The dedicated MCP client uses the same shutdown path as server telemetry. The SDK is pinned because MCP Analytics is still beta and minor releases can change behavior.

The browser integration inside the mobile WebView owns identified product events, session replay with every form input masked and the `ph-no-capture` account, security and administration screens left out, browser logs, and browser metrics. Server functions propagate the validated browser session into structured error logs and stable request spans, while request counts and duration histograms use only the method and outcome as bounded dimensions. The Expo shell uses a separate native client for application lifecycle events and native-shell exceptions when `EXPO_PUBLIC_POSTHOG_API_KEY` is set. Native screenshot replay stays disabled because it cannot redact the WebView DOM without masking the whole view. Production iOS builds upload native JavaScript source maps through the PostHog Expo and Metro plugins. Canary builds exercise the same native tooling in dry-run mode because the preview environment does not contain the native source-map upload credential.

Web builds generate hidden browser source maps. Hosted staging and production image builds use the pinned `@posthog/rollup-plugin` and `@posthog/cli` to inject chunk IDs and upload browser bundles, including the combat worker, before publishing the image. The plugin accounts for injected IDs in Vite's content hashes, so immutable asset caches cannot serve old bytes under the new build's URLs. The `praetorium-web` release version is the deployed commit SHA. The CLI receives its credential through a BuildKit secret rather than a build argument or a persisted image environment variable. Missing upload configuration or a failed upload stops the build. Pull request previews and local builds need no upload credential. Container builds remove public source maps, including previews, so they are not served to visitors. See [PostHog's CLI source-map documentation](https://posthog.com/docs/error-tracking/upload-source-maps/cli) for the credential scopes. Previously deployed bundles without uploaded maps remain unresolved, and this change does not merge existing issues.

## Event contract

Custom events describe completed user or domain actions, flow starts, submissions, and failure outcomes. Page navigation and ordinary clicks remain autocaptured.

`battle_command_submitted` contains the command kind and outcome. For `set-setup-step`, it also contains the bounded `setup_step` that was attempted; use `outcome = appended` to measure reached steps. Other command payloads stay out of analytics. `battle_created` also carries `player_count`, `practice`, and `casual` to distinguish table size and practice use. Datasheet metrics separate server work, request time, and render time. Performance events contain durations and workload counts only.

Onboarding events are the guide's own answers. The welcome, a finished tour, a skip and a restore are captured by the server function that records them, while the browser captures how far a tour got: `onboarding_task_started`, `onboarding_task_viewed` and `onboarding_task_paused`. A task the player finished by playing the game is folded from what they did and emits nothing; the event that would have announced it is already `roster_created`, `friend_request_accepted`, `battle_created` or `league_joined`. `task` is the bounded task id, `step` is the bounded step id, and `onboarding_welcomed` carries no properties.

`datacard_join` on datasheet metrics is `external-ref`, `name`, or `missing`. It measures whether the catalogue datasheet found its Game Datacards record and which join path resolved it.

`roster_created` is captured when a save inserts a row, which includes an empty list or a visitor's list claimed after sign-up. It does not prove the player added a unit. `roster_imported` records parsing, including unmatched factions and imports awaiting review; it does not prove a list was saved. `roster_import_saved` and `guest_roster_saved` are browser events emitted only after the save request succeeds. A guest claim retried after an uncertain response can emit `guest_roster_saved` again, so use unique people for conversion counts. `pick_count` on `roster_import_saved` counts the parsed picks, including attached characters separately.

Visitor events mark the start of a tab-local roster, the choice to save it through sign-in, and the successful or failed claim after authentication. `combat_simulator_opened` records one mounted simulator session with `source = standalone`, `roster`, or `battle`; edits and swaps do not repeat it. The simulator records the first successful estimate and the first failed calculation per open matchup, with the entry surface, result phases, and a bounded failure reason. Notification events record the saved preference or the bounded native permission outcome. League admission records the number accepted by a bulk action; moderation records only the accepted or rejected status. Friend rejection records the completed action without identifying the other player. Invite sharing records whether the native share sheet opened or the link was copied, without recording the link. `roster_import_shortfall_accepted` records a saved import after the player accepts missing or unplaced choices.

`unit_count` on a roster event is how many units the list fields, counting a character inside the unit it joined, as `attachedUnitCount` folds it. The events that measure a request rather than a list — `roster_priced`, `roster_imported`, `roster_exported`, `roster_datasheet_loaded` — count the picks in that payload instead.

Server-side roster events that have setup data carry `limit`, `faction`, `detachment`, and `detachment_count`. Faction and detachment values are normalized source names, not catalogue ids. `detachment_rules_covered` says whether every selected detachment has the rules-source semantics that Game Datacards does not supply; it is absent when no detachment is selected.

Server-rendered root and home loaders log their total duration when a loader exceeds one second. The home log includes bounded query durations. Neither log carries account identifiers or payloads. Use them to distinguish the shared session from feed and roster delays on a slow refresh. Onboarding progress loads after the document and does not hold up every signed-in route.

Creation funnels start when the player opens the roster, battle, or league creation form, and submissions fire for each attempt. Successful creation remains server-confirmed. `account_authentication_started` covers email and social-provider submissions with `action = create` or `sign_in`; it never includes the redirect destination. Failure events carry a bounded reason such as `request`, which does not distinguish a transport failure from a server rejection. Existing exceptions and request traces supply that detail. Builder events cover structural roster changes and failed autosaves, not successful autosaves or each loadout stepper click.

Search records an open, a settled outcome for each consecutive query of at least two characters, and a close. Repeated refetches of the same successful query do not add completions; recovery from an error records the subsequent success. `global_search_completed` carries `outcome = success` or `error` and the number of displayed results, including matching pages; errors report zero results. `global_search_closed` distinguishes selection from dismissal and includes whether a query was present, the displayed result count, and pending or failed state. Button, keyboard, and native opens share these events. Query text stays in transient UI state and never enters event properties. Imports separately record opening the form, submitting text, required review, and the final save outcome.

Every browser event receives `feature` and `surface` at the SDK send boundary. `feature` groups pageviews and actions into home, rosters, battles, leagues, factions, rules, missions, force-dispositions, simulator, friends, players, account, admin, data-updates, support, legal, navigation, or other. Detail pages share their parent feature; no route parameter enters this property. `surface` is `web` or `native` according to the WebView bridge. These properties do not apply to server or native-shell events.

## Privacy boundary

Analytics properties exclude names, email addresses, images, battle tokens, roster
ids, catalogue ids, search text, unit names, list contents, command payloads, rules
text, and error messages. They contain only bounded enums, booleans, counts,
durations, and non-sensitive outcome labels.

Errors may contain stack traces through PostHog Error Tracking. Manual exception captures add only an operation label. Server logs use stable messages and bounded request metadata rather than request bodies or URLs containing opaque ids. Request metrics contain a method, outcome, and duration; request spans use a stable name and never include the raw URL.

## Measuring success

Use unique people for conversion and retention; repeated attempts are useful for friction but are not additional converted players. Pageviews broken down by `feature` measure feature reach, while completed actions measure use. Compare browser `surface` values to separate web and native WebView journeys.

| Question                                                   | Event sequence or breakdown                                                                                                                                                                                  |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Where does account creation stall?                         | `account_authentication_started` with `action = create` → `account_created`; inspect `account_authentication_failed` alongside it.                                                                           |
| Do players get from an empty list to building an army?     | `roster_creation_started` → `roster_creation_submitted` → `roster_created` → `roster_unit_added`.                                                                                                            |
| Do visitors keep what they built?                          | `guest_roster_started` → `roster_unit_added` → `guest_roster_save_started` → `guest_roster_saved`; use `unit_count` to distinguish small and larger lists. Empty lists cannot start the save flow.           |
| Does importing lose players at parsing, review, or saving? | `roster_import_started` → `roster_import_submitted` → `roster_import_saved`; inspect `roster_import_failed`, `roster_import_review_required`, and `roster_import_save_failed` between those steps.           |
| Where does battle setup stall?                             | `battle_creation_started` → `battle_creation_submitted` → `battle_created` → `battle_roster_attached` → `battle_started` → `battle_finished`; break down appended `set-setup-step` commands by `setup_step`. |
| Do league organizers finish setup?                         | `league_creation_started` → `league_creation_submitted` → `league_created`. Entrant activation uses `league_joined` → `league_roster_submitted`.                                                             |
| Does the simulator deliver an estimate?                    | `combat_simulator_opened` → `combat_simulation_completed`, broken down by `source`; inspect `combat_simulation_failed`.                                                                                      |
| Does search help people reach something?                   | `global_search_opened` → `global_search_result_opened`; inspect successful zero-result searches and closes with `selected = false`, keeping pending closes separate.                                         |

A missing later event within a chosen conversion window indicates drop-off; a closed tab cannot reliably announce abandonment. Signed-out visitors retain the browser's anonymous identity, which the existing identity integration links after sign-in. Server completion events use the authenticated account id. Operational exceptions, replay, request metrics and traces, and sampled roster-pricing and datasheet-duration distributions explain friction. These events become available after the instrumented build is deployed; the code does not create PostHog dashboards.

## Saved dashboards

The Praetorium PostHog project has three dashboards for weekly review, each defaulting to the last 30 days:

- [Feature adoption](https://us.posthog.com/project/548119/dashboard/2162146): engaged players, feature use, browser feature reach by web/native surface, search friction, and new-event coverage.
- [Conversion and drop-off](https://us.posthog.com/project/548119/dashboard/2162147): account creation, roster creation, guest saving, imports, battle setup/play, league organizers and entrants, simulator estimates by entry source, search navigation, and failure diagnostics.
- [Player retention](https://us.posthog.com/project/548119/dashboard/2162148): weekly meaningful activity, new accounts returning to that activity, roster building, and accepted battle commands.

The shared `Praetorium meaningful activity` action combines structural roster changes and exports, accepted battle commands, league participation/setup, and successful simulator estimates. It excludes pageviews, authentication, administration, pricing/loading, errors, and MCP traffic. All charts apply the project's configured internal/test-account filters.

Funnels use ordered events from unique people, with a seven-day conversion window except search and simulator, which allow one hour. They measure a player's journey, not a particular roster, battle, or league: object ids are excluded, and different battle players can perform different steps. Retention uses weekly cohorts and observed returns in weeks zero through four, without cumulative retention. Recent cohorts and the first/current calendar weeks are incomplete.

New flow events and browser `feature`/`surface` properties require the telemetry deployment; their absence must not be read as user abandonment. After deployment, verify a real guest-to-authenticated save journey in PostHog, checking event duplication, identity linkage, and the privacy boundary. The coverage chart confirms arrival, not those guarantees.
