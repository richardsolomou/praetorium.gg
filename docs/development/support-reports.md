# Support reports

`src/core/supportReport.ts` owns the exact public payload and limits. `src/client/features/support/SupportReports.tsx` provides review and explicit public consent. The account menu passes only a page category; object URLs, rosters, battle state, account identifiers, emails and screenshots are never attached automatically. The initial attachment format is bounded text included in the exact issue-body preview. Private requests retain the privacy email route.

`spacetimedb/src/productSchema.ts` stores private requester/reference/delivery mappings. `support_report_command` accepts only the configured operator and scopes every read and write to the authenticated requester supplied by the server function. Account deletion removes mappings, not published GitHub issues. Support reports stay outside offline application snapshots and telemetry/replay payloads.

`src/server/supportReports.ts` saves the immutable reviewed report before one GitHub POST. Concurrent retries of the same reference return its existing state. A timeout, shutdown or unexpected response can leave delivery unconfirmed; it does not prove refusal. GitHub creation can succeed before the local finish transaction fails; the retained reference permits reconciliation without a second POST. Checking an unconfirmed report searches for its UUID, exact title/body and dedicated service-account author. Search is eventually consistent: an absent result never authorizes another POST. If triage changes the issue title or body before reconciliation, exact matching fails and requires manual investigation. A crashed process before POST may also leave an unconfirmed report requiring manual investigation; do not promise exactly-once delivery or silently republish it. Definitive GitHub refusals are shown as not sent.

Creation is limited to 100 reports per account and one new report per 30 seconds. Atomic checks permit one status/reply read per report per 30 seconds across replicas. Each check issues at most four sequential GitHub requests, each bounded to 15 seconds and 2 MB of response bytes, under a shared 25-second GitHub deadline. Replies use 30 comments per page, with at most 100 pages; the public issue remains available for longer threads. Replies render as text without remote images, HTML or automatically opened links. A completed GitHub issue is distinct from initial receipt.

## Credential and rollout

Keep reporting gated with the credential unset until activation is authorized. For that later activation, set the dedicated production secret `PRAETORIUM_SUPPORT_GITHUB_TOKEN`; the hosted workflow passes it as `SUPPORT_GITHUB_TOKEN`. Create a separate fine-grained token for this service, restricted to `richardsolomou/praetorium.gg` with Issues write and GitHub's required Metadata read. Its GitHub account needs repository access; a separate bot account is optional. No account-wide user permissions are needed. Never reuse a personal CLI token, the Sponsors token or a player's OAuth token. Rotate the credential before expiry, preserving its account identity so uncertain reports can still match their original author. GitHub App installation tokens are not supported by the authenticated-user reconciliation endpoint.

Without this variable, the app disables submission and keeps the public issue tracker and privacy email available. Staging and PR previews do not receive the production credential. Removing or expiring the credential does not erase local report mappings. An expired credential may appear configured but GitHub refuses writes and reads until rotation.

The default-off implementation can merge after the missing-credential fallback and additive SpacetimeDB migration are verified. This does not establish public delivery or complete #915.

Before enabling reporting for players, marking this feature ready or closing #915, verify a real authenticated submit → GitHub triage → public reply → player read cycle with the intended credential, plus account separation. Obtain explicit approval of the exact synthetic issue and reply before writing public QA content. Do not substitute an administrator's CLI token for runtime verification.

[GitHub's issue contract](https://docs.github.com/en/rest/issues/issues), [comments contract](https://docs.github.com/en/rest/issues/comments), [authenticated-user contract](https://docs.github.com/en/rest/users/users#get-the-authenticated-user) and [REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) define the versioned adapter boundary.

## Verification

Use the payload/transport tests and `src/server/supportReports.integration.test.ts` with the standard local SpacetimeDB test environment. The integration suite uses real local HTTP for a fake GitHub destination and real product transactions; it never posts to GitHub. `e2e/contextual-support.spec.ts` checks desktop/phone review, cancellation, consent, disabled configuration and the portalled preview's replay exclusion. Its configured recovery cases replace only support server-function responses to exercise uncertain-to-received and refused UI transitions; they do not establish GitHub delivery. Exercise status/replies and account changes with the intended credential before readiness. Verify failure assertions by removing the relevant guard: an authentication refusal from an invalid token does not establish operator authorization.
