# The interface

## Parity

The layout is matched against BattleBase; [docs/parity.md](../parity.md) records what is done, what is left, and how to re-derive it.

- **The interface follows BattleBase's information architecture on dark surfaces.** That is a deliberate choice — parity first, differentiation later — so a screen that departs from it needs a reason. Their density, their vocabulary (uppercase tracked headings, a count beside every section title, a bordered points chip after every datasheet name, a tick-and-total bar that never leaves the screen), their red-versus-blue sides; our near-black. The captures the layout was matched against are not in the repository, so re-derive from the live site rather than from memory before claiming parity.
- **BattleBase sets its type in ITC Conduit, which is Monotype's to license.** `src/styles.css` self-hosts Barlow Semi Condensed instead — squared grotesque, tall x-height, takes uppercase tracking the same way — vendored under `public/fonts` with its OFL text beside it. A licensed Conduit is a one-token swap at `--font-sans`. Never vendor a font whose licence is not in the same directory.
- **Squad size is edited on the card, not in the loadout pane.** It is the most common edit in list building and the least deserving of a trip to another pane — on a phone that pane is a whole screen away. It lives in exactly one place for the same reason panes do: two controls named "more models in X" are two controls to a screen reader.
- **`data-unit` is how a test finds a unit card.** The names on screen are uppercased by CSS, so the DOM holds "Overlord" while the page shows "OVERLORD" — matching on the visible text is a trap that has now cost two rounds of spec fixes.
- **A pane is one instance that CSS moves, never two that agree.** `builder/Pane.tsx` is a sidebar where there is room and a sheet over the roster where there is not. Rendering both put two of every control in the page — two fields labelled "add a unit", both real to a screen reader, and the strict-mode failure that found it was the accessibility bug complaining.
- **`src/styles.css` owns the bridge from the `:root` tokens to Tailwind's colour utilities** (`@theme inline { --color-primary: var(--primary) … }`). Without that block every `bg-card`, `border-border` and `text-muted-foreground` inside the generated components silently resolves to nothing and the whole UI renders flat.
- **UI is shadcn (Base UI) under `src/components/ui`.** Generated by `pnpm dlx shadcn@latest add` and excluded from lint. Treat as vendored: never hand-patch, wrap instead.
- **The side tint is information, not decoration.** Every number on screen belongs to one player, and across a table the tint is what tells you whose it is before you have read the name. Controls appear only on the viewer's own panel, which is the ownership rule made visible.
- Migrations are generated (`pnpm db:generate`), never hand-edited once applied. `drizzle/` is copied into `.output/server/drizzle` by the build so the production server can run them.
