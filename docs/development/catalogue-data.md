# Catalogue data

Community data supplies roster construction and reference records. Deterministic evaluation lives in `src/core`; source loading and contextual projection live in `src/server`. [Running locally](running-locally.md#catalogue) owns activation commands; [Game rules](game-rules.md) owns play/scoring semantics.

Offline construction bundles include each rules version's playable catalogues and their complete transitive imports, including the game system. The version 3 download format shares identical runtime data with its base source and repeated prose through a text table. Restore rules-version metadata before validating the downloaded bundle. Saved construction data retains those references and reconstructs only the selected rules version on demand. Bound both compressed and expanded data, and retain version 1 and 2 download support. Do not duplicate unrelated armies in each version or raise the bundle size limit to accommodate them. The build must decompress and validate the generated bundle with the client's decoder before writing it. Verify a production build with the release snapshot and exercise versioned roster editing after a cold offline reload.

## Sources and loading

| Authority                                         | Location                           |
| ------------------------------------------------- | ---------------------------------- |
| Upstream revisions, licences, and attribution     | `catalogue/sources.json`           |
| Pinned file composition and rules versions        | `catalogue/composition.json`       |
| Release snapshot pin                              | `catalogue/lock.json`              |
| Withdrawn snapshots/sources                       | `catalogue/revocations.json`       |
| Saved IDs from retired sources                    | `catalogue/retired-ids.json`       |
| Reviewed saved-loadout migrations                 | `catalogue/roster-migrations.json` |
| Authored corrections with provenance              | `catalogue/patches/`               |
| Immutable manifest, hashes, and canonical records | Verified snapshot                  |

Never commit fetched upstream files, copied rules prose, generated catalogues, or snapshots. Keep corrections minimal and source-pinned. Game Datacards extraction includes only the configured edition/game. Inspect the exact source before changing rules; unsupported or conflicting semantics remain reported, not guessed.

Rule references recognize both `Twin Linked` and `Twin-linked` as the same weapon ability while preserving the source's displayed spelling. Weapon abilities split on commas and semicolons, preserving colon-delimited target restrictions. The server, client, and combat reader share that splitting rule. Missing catalogue rule definitions fall back to unambiguous weapon and core ability definitions in Game Datacards' `keywords.json`; a datasheet's own named ability can also describe a weapon keyword. Granted core abilities retain their source note and use the same rule definitions for their tooltip.

`src/server/sync.ts` owns bounded downloads and extraction; `catalogueSnapshot.ts` owns archive packing/verification; `scripts/lib/catalogueMaterialize.ts` owns pinned source assembly. Stage complete output and replace it only after every source, correction, revision, hash, and required-content check succeeds. Do not replace an activated shared-cache symlink. Retry transient transport failures, not checksum or schema failures.

`pnpm catalogue:materialize` writes `.output/catalogue-data/` or explicit `CATALOGUE_DIR`; single-source output supports patch verification. Publication verifies the uploaded archive before changing `current.json`. Hosted images retain their packaged snapshot until deployment; publication alone does not update live rules. Health waits for catalogue/search preparation. An instance without data can still serve battles and pasted rosters.

Battlemaster materialization fetches detail and Chapter Approved lite data for every layout. Verify layout identity, slot, deployment, instance order, position, and rotation before joining objective codes. New lite files require publishing and pinning a new verified snapshot before deployment; older snapshots retain deployment-objective fallback.

Canonical catalogue output carries a compiler version. When its version is older than the application's compiler, startup recompiles the reference in memory from the verified snapshot's sources. Local generated output must match both the current compiler version and source revisions. Compiler fixes therefore reach reference pages on deployment without changing the pinned upstream data or editing the immutable snapshot.

### Composing sources and publishing rules versions

`catalogue/composition.json` selects files from independently pinned repositories. Its root `overlays` replace exact files in `definitions`, `points`, or `datacards` after fetching `catalogue/sources.json`. Every repository source uses a full commit SHA; `branch` is used for drift reporting, never as a moving download target. Include imported libraries and shared dependencies required by a replacement. Materialization rejects missing files, duplicate book IDs, duplicate overlay destinations, and missing imported books before replacing the output. It does not validate every upstream entry-ID collision or every rules interpretation; inspect the selected source and run the ordinary catalogue audits.

The composition selects the Praetorium fork’s `main`, which tracks BSData main. The Space Marines codex was [merged upstream](https://github.com/BSData/wh40k-11e/pull/2409) on 11 October 2026; the current rules snapshot pins main with the subsequent corrections. The retained 3 October codex version pins the previous base sources and Marine/chapter overlay, including its compatible shared game system and local Ceramite Sentinels correction. Keep those pins and its saved rules identity unchanged.

`richardsolomou/wh40k-11e` supplies definitions. Keep `main` as an upstream tracking branch; author new codexes on separate branches in that fork, preserving BSData identities and file structure. Select their exact commits as edition overlays when their data is verified. A branch created from current rules is only an authoring baseline; do not configure it as a preview until the new rules, points, and datacards are verified. Keep small verified corrections in `catalogue/patches/`; do not copy whole catalogues or rules prose into this application. Historical branch pins remain fixed even after their content merges into main.

Before checking upstream drift, fast-forward the fork’s main without force, then inspect its changes and advance the application pins deliberately:

```sh
gh repo sync richardsolomou/wh40k-11e --source BSData/wh40k-11e --branch main
pnpm catalogue:upstream
```

A divergent tracking branch must be investigated rather than reset. Syncing the fork does not move the application’s pinned commits or publish a snapshot. Source changes to released versions require retaining their effective source pins and adding a new current version through the verified publisher.

Correction contents contribute to source revisions; edition revisions also contribute to the combined faction-cache revision. A correction-only publication must invalidate saved-roster pricing, totals, and legality caches.

Each `editions` entry contains an `edition`, optional whole-source replacements in `sources`, and file `overlays`. An edition needs a stable lowercase `id` (at most 20 characters), player-facing `name`, `status` (`preview`, `released`, or `retired`), `default`, original playable `catalogueIds`, and `releases` events with epoch-millisecond `at` and `status`. Use a new edition for a codex, MFM points update, or other rules revision that players can select separately. Set preview `default` to false; only released editions can become the default. No unreleased production edition is configured until verified source data is available. Rules history labels these immutable events as recorded catalogue status changes; their dates do not establish publisher release or effective dates. Keep those date authorities distinct.

Name rules versions after verified releases such as an MFM version or codex; never use “Previous rules”, “Original loadouts”, or similar relative or internal names. Show the default first in every rules selector and mark it “Current”. Verify names against the pinned upstream branch. MFM release dates use `firstSeen` and the BSData version changelog. Codex dates can come from publisher announcements or corroborated retailer release listings; distinguish pre-orders, scheduled releases, and actual releases. When retained catalogues share an MFM release, use the pinned source revision date in the name and explain the snapshot date and MFM release date in the edition description shown by its tooltip. Keep technical qualifiers such as “Catalogue” out of player-facing names. Retirement and compiler timestamps are not rules release dates. A named `base: true` edition aliases the root sources: offer it once in selectors and the combined reference, while continuing to resolve exact root IDs for saved rosters and old links.

The Space Marines codex release on 3 October 2026 is supported by the [publisher's 27 September announcement](https://www.warhammer-community.com/en-gb/articles/zuwukdba/sunday-preview-might-of-the-ten-thousand/) and [Loaded Dice's release listing](https://www.loadeddice.uk/products/codex-space-marines-11th-edition). The Custodes codex is scheduled for 17 October 2026, corroborated by [Miniature Market](https://www.miniaturemarket.com/Codex-Adeptus-Custodes-Preorder/GW-01-14-2026) and [Pandemonium Games](https://www.pandemoniumgames.co.za/collections/games-workshop/products/warhammer-40k-horus-heresy-adeptus-custodes-codex); it remains a preview. Catalogue dates for retained MFM 1.4 and 1.5 versions refer to their exact definition revisions [659a6027](https://github.com/BSData/wh40k-11e/commit/659a6027f7b192d3a21a630b1c9786ae29ec741f) and [6cd87e7c](https://github.com/BSData/wh40k-11e/commit/6cd87e7c53badbac33773587d4fbee8fe06a023c).

An edition inherits the composed root definitions, points, and datacards unless explicitly replaced. Verify all three authorities together: inherited MFM rows and prose can otherwise override a new codex's definitions. Pin or overlay edition-specific points and datacards when they differ. Root corrections apply before inheritance; edition corrections belong in `catalogue/patches/editions/<edition-id>/<source>/`. Both layers use the existing provenance requirements. `pnpm catalogue:materialize --source definitions` applies root composition for patch verification and omits editions; complete materialization builds isolated indexes under `editions/<edition-id>/`.

Authored points and faction datacards can declare an `attribution` string. Reference datasheets and detachments retain that attribution instead of crediting authored content to the inherited MFM or Game Datacards source. Keep preview uncertainty and unsupported semantics documented in the authoring repository; an official-looking file shape does not establish source authority.

Players choose a rules version within the faction. Its index controls units, detachments, enhancements, pricing, and references together. Changing rules versions retains selections and reports unavailable choices for replacement. Every setup-save consumer, including library actions, compares faction families and remaps allied catalogue identities before saving. Rules reads carry the selected catalogue ID through optimization and reference previews. Saved lists and exports carry `<edition-id>~<book-id>`; unit and option IDs remain unchanged. Ordinary faction URLs, global search, and simulator pickers use the default rules. Exact saved IDs retain their selected version. Rules-version paths use `/factions/<faction>/rules/<slug>`: editions can declare a stable `slug` separately from their saved ID, while root MFM rules use `mfm-<version>`. Published slugs cannot collide with edition IDs or change after publication. Existing edition-ID and qualified catalogue-ID paths, including nested datasheets and detachments, and earlier `?rules=` links redirect to the selected version's canonical path. The unversioned faction path opens the default rules. `FactionReferenceLink` preserves this selection across datasheets, detachments, breadcrumbs, and new-tab links. Route loaders resolve slugs to the exact catalogue ID before reading data; unknown versions fail rather than falling back. Previews are labelled in lists and reference pages and cannot be submitted to leagues; ordinary battles can use them. Battle snapshots freeze the rules-version label/status with the army, including linked lists whose prices are read from current data. Older snapshots without version metadata show no version label.

Existing rosters retain their selected version when the default changes. The builder and library offer “Convert rules version” to update the same roster deliberately, including conversion to archived versions. Preserve its units, choices, relationships, name, access, and preparation; check destination pricing and legality through the existing evaluator. Unavailable choices remain visible for replacement. Keep the original root source pins unchanged when publishing a new rules package, and pin all source authorities for retained editions so inheritance cannot change archived rules. Publish a points revision such as MFM 1.6 as a distinct version rather than editing MFM 1.5 in place.

To promote a preview, keep its ID and files, append a `released` event, set `status` to `released`, and set `default` to true. Turn off the previous edition's default if one exists. Do not rename, delete, or copy the preview into the root. Publication checks the previous verified snapshot and refuses removed editions, removed faction identities, rewritten release events, or changed effective source pins for a released or archived version. Retire superseded editions while retaining their sources for saved lists. Exact qualified reference routes can read imported support books without offering those books as selectable editions. Keep attachment, leader, supporter, and detachment destinations in the same rules version, including links from other factions and offline reference data. Data-update history compiles each version separately, including inherited units and detachments offered by its playable factions, so promotion preserves its history and does not create phantom unit additions. Saved-list change assessment compares only history from the selected rules version. Publish through the existing verified snapshot workflow; editing the authored manifest alone does not update hosted data.

### Retired sources

A retired source stays a known snapshot source name in `catalogueSources.ts`, so published snapshots that carry it still verify as history; it is never materialized again. When its records move to another source, `catalogue/retired-ids.json` maps each saved book, detachment, and datasheet ID to the current record with the same name in the matching faction, and each saved option and toggle to the one option or toggle of the same name on the mapped datasheet under the same detachment. Map only verified one-to-one matches and leave the rest unmapped, so pricing reports them as choices to reselect. `src/core/retiredCatalogueIds.ts` applies the map at each boundary where ids arrive: the server input schemas in `schemas.ts` (prices, saves, datasheets, simulations, battle faction and stratagem reads), saved rows (`rosterPersistence.ts`, library summaries), and stored guest drafts.

## Roster migration rehearsal

Before changing catalogue sources or saved-selection construction, fetch production rosters using [Production roster copies](running-locally.md#production-roster-copies). Run an audit with the existing code and catalogue, then retain that report before making changes:

```sh
just rosters-fetch
just rosters-audit
cp data-dev/production-rosters.audit.json data-dev/production-rosters.baseline.json
just rosters-import
```

An initial audit exits nonzero if it finds unresolved selections, unavailable detachments/catalogues, or clamped model counts. It still writes the complete report. Review and retain that baseline so existing problems do not conceal newly introduced ones. Keep the same production snapshot throughout a rehearsal; fetching again requires a new baseline.

After the change, compare against the recorded baseline:

```sh
just rosters-audit data-dev/production-rosters.json catalogue-data data-dev/production-rosters.baseline.json
```

The comparison exits nonzero for new identity losses, new unavailable detachments/catalogues, newly clamped saved model counts, newly exceeded point limits, or new unit/detachment legality errors. It also reports every points change. Reports include exact pick positions, choice keys and option IDs, imported local IDs, source revisions, points, and pricing errors. Review points and legality changes as well; an identity check does not prove the roster remains legal. Baselines record previous results, so a changed compiler or migration cannot rewrite the earlier assessment. Explicit catalogue directories allow testing a staged snapshot without activating it.

Author verified replacements in `catalogue/roster-migrations.json`, in chronological order, with the old and new verified snapshot IDs and a concise reason. It uses the same catalogue, detachment, datasheet, choice, spread, and toggle mapping format as retired IDs. `currentPick` applies retired-source mappings first and these migrations afterward at the existing saved-row, server-input, offline, and guest-draft boundaries. These mappings apply only to the current unqualified catalogue; retained edition loadouts keep their own source IDs. A normal save persists the translated selections. Never infer replacements by fuzzy name matching at runtime, substitute a different enhancement, or drop a removed selection to make an audit green. Preserve option counts, model slots, attachments, and unknown choices; require a player decision when there is no equivalent.

Verify each authored mapping against both snapshots' exact source records. Add a regression test that fails on the old paths, builds the migrated selections against the pinned catalogue, and checks repeated migration. Import the untouched snapshot, inspect affected rosters and loadouts in the running preview, save a migrated copy, and reload it. Report every unresolved item before deploying a catalogue update; test results alone do not settle removed or changed game rules.

Rules-version selectors group factions through verified retired catalogue aliases, including factions whose book ID changed. Deliberate conversion to current rules translates verified unit and allied-book identities while retaining equipment counts, attachments, and unknown choices. Builder and library conversion use the same operation; archived reference routes resolve the selected version's original book ID.

Retained editions can pin an immutable `snapshot` instead of inheriting current data. They cannot overlay or replace its sources. `catalogue/retained-roster-rules.json` selects the original edition from exact removed detachment or saved-selection signatures before equivalent path migrations. Each selection group must match at least one saved choice; zero-count options do not match. Normal saves persist that edition. A visible roster notice explains that it uses previous rules and opens the existing deliberate conversion flow; it does not claim current-rule illegality without evaluating the destination. A `base: true` edition names the pinned root rules without duplicating their source files or offline construction data. Conversion to that qualified current version persists the player's decision and does not automatically select previous rules again. Published base editions retain the root source pins under the same continuity checks as other released editions.

Startup prepares canonical reference records only for each edition's advertised factions. Exact support-book reads compile and cache that faction on demand, retaining the complete rules index for imports and relationships. Do not compile unrelated armies from every archived source before health can succeed.

Every configured rules version's complete catalogue, datacards, and rules stay loaded for the process lifetime, so each retained edition adds to every replica's resident memory. Loads that retain parsed sources read them through `src/server/sharedJson.ts`, which keeps one copy of each repeated string within a load instead of one per occurrence. It also returns the value already parsed from byte-identical content while anything holds it, and `editionCatalogueFiles` copies only the source objects that name a qualified book, so rules versions share unchanged books and entries. Treat parsed sources as read-only. Rules versions reading the same unchanged Battlemaster files share one geometry object per layout, so treat loaded geometry as read-only and copy before adjusting it. Compare heap use with and without a change using the same catalogue snapshot before claiming a memory reduction.

`scripts/retainRosterCatalogue.ts` reproduces historical profile construction with the exact compiler commit and source/icon snapshots in `catalogue/retained-profile-build.json`. Run it with verified source and icon directories and a new output directory. Its archive retains the original datacard exclusion policy in `reference-policy.json`; server and offline construction apply that policy to defining books, including borrowed units. Publish and verify the immutable archives before pinning them in a release. Preserve saved loadouts even where the original dataset itself reports a legality error; never suppress the error to pass a rehearsal.

## Canonical catalogue and audits

`src/server/canonicalCatalogue.ts` compiles a validated, deterministic artifact with field provenance and issues. Reference pages consume it; contextual rosters still use the evaluator. `src/core/datasheetStructure.ts` owns semantic profile/characteristic kinds, keeping upstream display labels out of UI control flow.

| Field                                                               | Policy                                                                                           |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Executable choices, constraints, contextual modifiers               | BSData evaluation                                                                                |
| Printed composition, loadout, base, mission/rules prose             | Game Datacards, with supported source-backed fallbacks                                           |
| Reference and evaluated unit points, DP, enhancement/upgrade prices | Pinned MFM when an unambiguous row joins; supported card/evaluator fallback                      |
| Wargear prices                                                      | MFM only for matching executable options or source-backed pieces; remaining costs stay evaluated |
| Terrain geometry                                                    | Pinned Battlemaster detail and lite objectives; source-pinned label corrections                  |

Do not treat one source as globally authoritative. Replacement profile/ability joins must be unambiguous and preserve selected equipment/context. Conditional price rows require their actual model count and requisition context. Reference copy tiers retain source labels; unlabeled ranges follow the existing MFM wording, such as “Your 1st To 3rd Units Cost” and “Your 4th + Unit Costs”. Apply the same fallback when reading packaged canonical records, without rebuilding the catalogue for a label correction. Check sibling reference pages before choosing fallback wording for source omissions. Conflicts, missing joins, unsupported labels, and fallbacks remain visible in provenance and `issues`; unknown semantic mappings require a reviewed mapping and test.

```sh
pnpm catalogue:compile
pnpm catalogue:audit -- --details
```

Compilation writes `.output/canonical-catalogue.json`, outside the activated cache. Set `CATALOGUE_CANONICAL_FILE` for another path. Audits report the current snapshot; keep their changing counts outside these docs.

## Books and datasheets

Books offer root-linked datasheets, not every entry of a certain type/depth. Follow catalogue imports only when enabled; library books are not player factions. Separate an entry's defining book, books offering it, and its public reference home. `isReferenceDatasheet` supplies the shared discovery answer; conditional granted faction keywords do not create new homes.

Faction-scoped aliases and declared parents resolve rules and detachments. Do not adopt another faction's detachments merely because a catalogue imports it. Parent copies link to the parent's canonical page; chapter-only records retain their own page. Saved retired faction/detachment IDs remain present and illegal until deliberately replaced, never silently dropped or priced as free. Legends are excluded from legal picker choices.

Descriptions and ability definitions require exact, unambiguous joins. An empty named section is not permission to borrow matching prose from anywhere: a complete matching definition must belong to the correct faction/section. Missing enhancement/stratagem details finish loading as unavailable. Unit upgrades and character enhancements stay distinct, retaining source eligibility.

Missing army-rule prose can use an unambiguous matching BSData rule from the faction's books. When the faction has no army-rule cards or no Game Datacards file, only a sole visible top-level catalogue rule can supply the unnamed army rule. Library catalogues do not create factions; ambiguous candidates stay unavailable. `catalogueArmyRules.ts` owns this fallback, verified through `rules.test.ts`.

`GAME_SIZES` is a stable saved-roster/command protocol, not replaced by mission-pack size records. Source construction constraints remain authoritative.

### Custom points budgets

A saved roster's `limit` is its battle size; an optional `pointsBudget` replaces only that size's points total. `src/core/battle.ts` owns the bounds and helpers (`pointsBudgetError`, `pointsBudgetOf`, `customPointsBudget`); `saveRosterSchema` and the product module validate the same rule, and a budget equal to the size's total is stored as no budget. Core rules 25.03 say the battle size sets the points total, detachment points, enhancement limit and unit limit; the pinned game system models the override the same way, as a "Points limit" inside its Battle Size selection with a 500-point minimum and no maximum. So the battle size alone drives `battleSizeSelection`, detachment points, enhancement and datasheet limits and allied points caps, while the points-limit check (`rosterUseProblem`) and the frozen strategic reserve limit (50% of the points limit, rule 20.01) read the budget. Budgets are whole numbers from 500 to 10,000. King of the Colosseum fixes its total and takes none, and a 3000-point Onslaught keeps its existing unlimited detachment points even though the game system data gives it 4 DP.

An unstated budget is not a cleared one: a save, queued offline save or captured battle roster from a client that predates budgets keeps the stored budget, while `null` restores the standard total. Saves, durable local saves, the lock comparison, copies, variants, conversion and setup review all carry the field. League events refuse rosters with a custom budget.

### Collection

A player's collection is datasheets with a count of physical models, independent of rosters. It never changes pricing or legality. Every datasheet in a collection holds at least one model: adding starts at one, counting cannot go below one, and removal deletes the entry and its count after confirmation. Datasheet hearts saved before favourites existed are collection rows without a count; `moveHeartsToFavourites` in the product module moves a player's rows to favourites before any of their collection or favourite reads and writes, so the collection only holds counted models. Counts are bounded by `MAX_COLLECTION_MODELS` in `src/core/collection.ts` and stored on the membership row.

Manage collection membership on the Collection page or a datasheet page; roster unit menus offer duplication and deletion. Favourites are separate. The heart on datasheet rows and in the picker stores a `favourite_datasheets` entry; favourites list first in the picker and the reference datasheet list and say nothing about ownership. The picker's Favourites and Owned filters are unavailable, with a tooltip saying why, until the player has a favourite or a collection entry.

`/collection` (`src/client/features/collection`) groups the collection by faction through the combat unit index, adds datasheets, edits counts through a numeric field with plus/minus controls, and removes entries. Direct counts save on Enter or blur, reject values outside 1–10,000, and Escape restores the saved count. A datasheet page's Add to popover offers a roster, favourites, and the collection with its count. Suggestions come from the player's own armies in their 200 most recent battles, counted once per battle; they are optional and must not block the page when the read fails or the app is offline. Verify adding, counting, removal, suggestions and the offline journey through `e2e/collection.spec.ts`.

Collection and favourite edits save to the account’s durable queue before projecting into query data and return without waiting for server acknowledgement. Reuse saved documents rather than downloading the old value before each edit. Account downloads must pass retention checks before entering the query cache, so an older download cannot flash over a newer edit. Removal clears the saved model count in the same transaction as membership. Verify rapid edits under delayed acknowledgements as well as save/reload.

The Collection profile tab groups model counts by faction through `groupCollection` in `src/core/collection.ts`. A collection is published until its owner turns off Show collection on profile in the account settings (`src/client/features/account/CollectionSharing.tsx`); a player without a `collection_sharing` row gets `DEFAULT_COLLECTION_PUBLISHED`, and an explicit choice is kept. `collection_profile` checks publication and ownership in the same transaction as reading the rows. Public collection signals refresh other readers after edits, sharing changes, and deletion. Verify default publication, hiding from settings, public and signed-out reads, revocation, model counts and phone layout through `e2e/collection.spec.ts`.

`collection_stock` is retired. SpacetimeDB refuses to drop a table that still holds rows, so it stays in the product schema and in account deletion until it is emptied.

## Building units

- Required models come from the datasheet and cannot be invented by excess weapon counts. Only supported optional specialists may enter through equipment choices. Count all loadout variants of a required model kind.
- Collective counts are unit totals; parent-scoped counts scale with carriers. Mandatory model templates stored once still satisfy per-model minima. Every consumer uses `collective.ts` rather than multiplying independently.
- Defaults distribute required group counts within option caps, preferring declared defaults then supported cheapest choices. `refit` fills required equipment after resizing, never optional groups or model groups.
- A full group's increment reduces an available sibling; decrement returns capacity to its default. A model override clears other model slots first. Bounds may live on the group or occupants and apply to the total.
- Apply loadout choices before nested weapon spreads, then model allocations after specialists. Removed loadouts suppress nested equipment; restoring them preserves saved choices. Fixed/default equipment remains readable without duplicate controls.
- Fixed composition alternatives use the model-count control once. Resizing must retain unambiguous equipment choices without restoring an inactive composition, and the saved-choice validator must use the same resolved paths as construction. Exercise grow, shrink, another weapon edit and reload; verify one composition's price and matching model/equipment counts.
- Retain checked picker rows while edits are repriced; additions still wait for current limits. Clear retained results when the army setup changes. Verify pending, failure and retry states at desktop and phone widths.
- Equipment counts multiply ordinary ancestors once. Empty containers are not weapons, and linked profiles do not merge distinct carriers. Preserve independent choices and paired equipment as their actual bundles.
- Reminder timing is prose-derived suggestion, confirmed by the player. Unknown wording stays blank; each trigger keeps its own moment, phase, and turn scope. Round boundaries have no phase or turn owner. Explicit first-round wording suggests a first-round restriction; generic phase boundaries suggest “Any phase”. Explicit destruction conditions can suggest retaining the alert while the unit is destroyed, with player confirmation.

## Pricing and legality

`evaluate.ts` reports unsupported semantics in `unhandled`; unreadable conditions fail closed. Pass the full force, selected book, detachment, battle-size selection, bearer, and attachment context. Preserve selection order for escalating costs. Conditions counting selections flatten containers appropriately while group tests retain membership.

`keywordIds` applies written and granted/withdrawn categories consistently. Grant conditions use written links so traversal order cannot change the result; conflicting grants/withdrawals use source order. Hidden categories never become displayed keywords. `keywordsIn`, `restrictedBy`, and the evaluator are shared by visibility and legality. Error-field modifiers are legality errors. Known irrelevant shelf operations do not become validation warnings.

A datasheet's maximum on its own selections in `parent` caps the force holding it, as BattleScribe reads it. Choices come from definitions, including absent optional groups. Shared group caps and per-option caps are different; optional equipment competes only when a group cap says so. Warlord is a toggle governed by the bearer's conditions, not a weapon option. Force-wide limits must remain enforced even where catalogue composition problems are tolerated inside a unit.

Authoring an ability's prose does not apply its benefits. Encode permanent characteristic changes, selected equipment effects, added weapons, core ability grants and detachment grants through the existing catalogue evaluation paths. Verify displayed and saved/reloaded selections with and without each optional benefit, every supported model-count variant, and an unaffected sibling unit. Keep conditional, aura and once-per-battle effects conditional; an invulnerable save restricted to ranged attacks must not replace the unit's unconditional save.

Evaluate detachments before units and include the selected battle size in every force. Enhancement limits use the force's cost/constraint semantics, not a separate manual counter. `attachedUnit` groups bodyguard, Leader, and Support for unit-wide evaluation. Profile modifiers retain base values and source labels. Never apply already projected ability/stat changes again in combat.

Detachments are ordered purchases; every purchased detachment contributes DP and rules, while the player chooses one offered force disposition. Waivers use `formatRules` and remain visible through library, chooser, league confirmation, and battle snapshot. Optional rules use `optionalRules` and apply only by explicit selection; they are not implicit format rules.

King of the Colosseum construction follows [the publisher](https://playontabletop.com/kotc/), with its product size and retained legacy limits defined in code. Keep source restrictions separate from the optional borrowed-disposition homebrew. ## Saved lists and interchange

Each pick may carry its owner's private `note` (500 characters), bounded by `rosterPickSchema` and described in `src/core/unitNotes.ts`. An owner can lock a saved roster. `src/core/rosterLock.ts` decides that a locked roster refuses any save that changes its content (units, loadouts, setup, rules version, name or preparation) and accepts a save that changes only visibility. Deletion keeps its ordinary confirmation and does not require unlocking. Call this state Locked; league seals and battle snapshots are separate frozen copies. Exercise lock, refused edits, copies, unlock and an offline edit refused after another device locks in `e2e/roster-lock.spec.ts`.

Variants are independent saved lists in a flat `baseRosterId` group, copied from the server's saved row. Saves cannot change that identity. Automatic names update with edits; manual names stay chosen. Battle/league snapshots and exports freeze the name they received.
