# Catalogue data

Pins live in `catalogue/composition.json`, `catalogue/sources.json`, and `catalogue.json`; corrections in [`catalogue/patches/`](../../catalogue/patches/README.md). [Running locally](running-locally.md#catalogue) covers setup.

## Rules text

- Never serve or show either source's rules text in any form, construction data and the offline download included: the browser never loads them either, and every rule a player reads is a VS Data summary. Read Game Datacards strings through `SourceTexts` (`src/core/sourceText.ts`); the catalogue reads BSData's rules texts as tokens from load (`src/server/definitionTexts.ts`). Whatever a rule reads from words is recorded in `TextFacts` (`src/core/textFacts.ts`) and read through `readText` or `statedIn`, so the server and a device answer alike: a card rule's combat reading is recorded beside its token, or, for a rule of several tokens such as a stratagem, under all their keys (`factsKey`); `scripts/clientText.integration.test.ts` enforces this.
- A catalogue text Game Datacards prints too is published as the card's token where the card is the same VS Data record as the catalogue text (`src/server/cardTwins.ts`); a device acts on a token only through its recorded facts.
- Only the server reads BSData tokens back into words (`definitions.words`), to search what abilities do; such fields never leave it.
- Snapshots contain rules text: publish them only to the private `praetorium-catalogue` bucket, which holds nothing else. Test runs, `catalogue.yml`'s build and pull request previews read it with `R2_CATALOGUE_READ_*`, a read-only key for that bucket alone, so no pull request's code reaches the backups or players' photos in `praetorium-private`. `catalogue.yml` only builds a branch's snapshot; `catalogue-publish.yml` then publishes it with `R2_CATALOGUE_PUBLISH_*`, running `main`'s code alone, and pins it on the branch ([storage keys](../deployment.md#storage-keys)). A preview receives the read key as `SNAPSHOT_R2_ACCOUNT_ID`, `SNAPSHOT_R2_ACCESS_KEY_ID` and `SNAPSHOT_R2_SECRET_ACCESS_KEY`, which only `catalogueR2Client` reads, so no other bucket's client takes it up; production's server receives the publish key under the same names.
- Rules summaries come from the pinned [VS Data](https://github.com/richardsolomou/vs-data) releases in `catalogue/sources.json`: the current rules version's under `summaries`, and one for each earlier rules version under `summaries.earlier`, each by tag, archive and SHA-256. Materializing checks each archive's SHA-256 before unpacking, runs VS Data's own verification, refuses a release whose rules version no rules version in `catalogue/composition.json` is named for, and keeps only `summaries/<rules version>.json`, for the versions the build holds: a build without the private store, such as a preview's live refresh, verifies the releases of the versions it leaves out and keeps nothing of them: the summaries, their spans and open questions, a Stratagem's When, Target, Effect and Restrictions parts where its summary is written in them, the aliases the join needs, the credits adapted records carry, each Stratagem's typed facts and the mission packs. Each rules version plays its own release's Stratagems; every rules version plays the base release's mission packs, whose summaries `ruleSummaryRecords` serves under `missions` by `kind:id`. A new release is a change to its pin alone: while the `VS_DATA_LIVE` repository variable is `true`, `.github/workflows/vs-data-live.yml` opens that change every three hours (`scripts/updateVsDataPins.ts`) and merges it only once its snapshot is pinned, `scripts/checkVsDataCoverage.ts` finds no count fallen (the snapshot build and CI only report it) and the required checks pass, so a release the snapshot build refuses stays an open PR; unset it to pin by hand. Records join Game Datacards through VS Data's identity aliases (`src/shared/vsData.ts`), including the faction and wargear-slot forms for datasheets several factions print; each rules version's cards read its own release, and a file several rules versions print alike reads the base's. A full materialize then drops any summary that repeats a sentence of either source's files for its rules version (`withholdCopiedSummaries`), so a server never scans them. `ruleSummaryRecords` serves one source file's summaries by the hashes its tokens name, reading a rules version's release only once a rule of it is asked for; summaries are for reading, never game calculations. A token's file ID hashes its upstream address, revision included, so a data update replaces the file every stored token names: `ruleSummaryRecords` marks such an ID `replaced`, and the reader finds each string's current file through `textHomesFor` (`useRuleSummaries`). A summary is VS Data's restricted Markdown (paragraphs, lists of lines starting with a dash or a number, bold, `vsdata:` links), read by `src/core/summaryMarkdown.ts` into blocks the server serves, so a client never parses it; a release from before the Markdown carries offset spans instead, read the same way until no pin needs them. A Stratagem's summary written in parts is served as its parts alone (`RuleSummary.parts`), which every view of a Stratagem lays out under its labels and agents read apart; a reader wanting flat blocks joins them with `ruleSummaryBlocks`, so the words travel once. A summary without them shows as written. A summary shows uncredited in place of the rule, and a rule without one shows its name and numbers only; the Sources page carries VS Data's credit, and credits any upstream work a pinned release's records adapt (`ruleSummaryCredits`), so a credit leaves once no record needs it. A detachment's rules, Enhancements, upgrades and Stratagems show the summary of their VS Data id (`useVsDataSummaries`), in their rules version's release, else the current one's: a Stratagem's own id, an Enhancement or upgrade the builder offers by the frozen maps, and a reference card by the VS Data alias of its Game Datacards card (`vsDataId`), or by the frozen maps for one only the prices name, which also keeps a card BSData spells otherwise from showing twice. A detachment rule no Game Datacards card prints, like any other rule whose text only BSData prints, finds its summary by name through its owner (`useUnitAbilitySummary`): the datasheet's VS Data unit or the detachment (`<faction>.<detachment>`), then its faction, then the one faction that has it; a core rules clarification is a record of its own (`gdc.core.rule.clarification.<rule>.<number>`), or the FAQ whose words it prints. Weapon and core abilities a summary names, by span or in brackets, open the current rules version's summary of that ability (`ruleAbilitySummaries`), which a keyword tooltip also falls back to by name where its own text has none. A rules version's release names its weapon and core abilities (`keywords`), the keyword glossary: a keyword the catalogue prints no rule for, or a core ability a faction lists among its army rules, is that ability, with no text, and shows its summary by name. The rules pages are the rules documents each release outlines in its `core-rule` records (`vsDataRuleDocuments`), in the order, sections and anchors VS Data gives them, with their summaries served under `rules` by `kind:id`; a link or `rule:` reference id made before then may name a rule by its Game Datacards id, which `catalogue/legacy-ids/rules.json` resolves, and a document or section by its id, which `rule-pages.json` resolves. A datasheet's base size is the one its rules version's release types for each stat line (`baseSizeOf`); where it types none, as for the Warhammer Legends datasheets no official source sizes, the canonical catalogue shows BSData's until a VS Data release carries them (#2009). `pnpm catalogue:points` ends with `scripts/checkVsDataCoverage.ts`, a ratchet per rules version on `catalogue/vs-data-coverage.json`, which also counts the current catalogue's weapon ability keywords whose tooltips show a summary.
- Materializing also keeps each release's typed effect blocks (VS Data's `docs/rule-facts.md`) beside its summaries, as `summaries/<rules version>.effects.json` by `kind:id`, with the rules a block references by name and any block Praetorium cannot read held back as unresolved. They are what every rule does: loading a rules version joins each text its catalogue holds to a VS Data record (`src/server/vsDataEffects.ts`: the record its card's identity aliases, else the one the BSData rule or profile holding it is, by VS Data's `bsdata.*` alias or the frozen per-datasheet map (`vsDataRecordOfBsdata`); never by name), a text several datasheets print alike, each a unit's own record named for one core keyword rule (as a Damaged bracket), joining that core rule's record, which names the rule so the datasheet lists it and reads that record's blocks into the catalogue's `TextFacts` (`textFactsOfVsData`, `src/shared/vsDataEffects.ts`), which a device downloads alike. A text that joins no record, or records saying different things, calculates nothing, and neither does one whose record keeps no combat block or a reading without choices: its words give only the roles it takes (`combatOfVsDataOrWords`), so the simulator lists it as not calculated, as VS Data asks. Leader, Strategic Reserves and unit-held wargear facts (what a card says the unit has rather than a model, as a Plasmacyte, which marks out no bearer in a battle's model lines) still come from the words until lists are built from VS Data. Holders that share a text must agree on its record; a reading that only leaves `reachesAttached` off a unit no Leader joins agrees with one that has it. `textFactsOfVsData` starts each placement on the choice Praetorium's own reading would, reads a keyword a rule grants as an ability of that name, keeps a grant only the units a player picks as the battle begins gain (`picked`) out of what any unit holds and offers it in battle setup instead (`pickedGrants`, the priced units' `grantPicks` and the `pick-unit-grant` command), and keeps a bearer-only effect on its weapons, characteristics or damage to the leader it belongs to in an attached unit (`withBearerEffects`), though a hit or wound modifier on attacks against the unit still reaches every group. An effect VS Data limits to some models (`modelKeywords`, `excludedModelKeywords`), or a wargear ability's bearer-only effect, reaches only those models (`effectModels`, matched by each carrier's keywords, name and the wargear abilities it holds): an attack effect goes onto the weapons only those models carry and leaves out a weapon others carry too (`withModelAttacks`), and a defence effect splits the models it reaches into allocation groups of their own (`combatUnitTarget`). It calculates no Wounds changes or mortal wounds outside the attacks, as the simulator cannot yet. A reading with an effect it cannot apply yet (a weapon's range, dice added to, set as or multiplying a characteristic, a set unit characteristic, a weapon ability the attacks lose or an effect only for weapons without one) is not calculated, and an invulnerable save that holds against ranged or melee attacks alone shows on no datasheet. A catalogue text that only names its datasheet by a shared profile, as a Damaged bracket, or that VS Data has no record for joins nothing until lists are built from VS Data.
- Materializing also keeps each release's roster definitions, datasheet profiles and points snapshots whole, by kind and ID with their names, as `summaries/<rules version>.construction.json` (`writeVsDataConstruction`, read by `vsDataDefinitions`), with each Enhancement as its rule facts' `enhancement` block under its Detachment, the units the identity marks absent or retired (`unavailable`), and the one unit each retired unit is replaced by (`replacements`), which a saved ID reads as (`definitions.current`). `src/core/vsDataRoster.ts` is VS Data's `checkRoster` and `lookupPoints` (`src/core/vsDataPoints.ts`) on that file, apart from three readings: an Enhancement's eligibility is its rule facts' (a CHARACTER, not an EPIC HERO, unless the facts say otherwise), borne by a fielded model with its unit's keywords and its own; a priced item costs for every one the unit carries, by default or inside a bundle; and the points limit and Detachment points stay `battleFormat.ts`'s format rules, which a roster may waive and which cap Detachment points across every Detachment a list holds, a lone one included. Where a unit has several cost rows at its size, it takes the one naming one of the roster's Detachments, else the one naming the roster's army (its faction or parent), else the one for other armies (`as …`), else the one naming its model counts, else the one row naming none of these (`costRowFor`); a row naming another army never applies.
- The current rules version's datasheets print VS Data's stat lines (`vsStatLinesOf`, `src/shared/vsDataProfiles.ts`, packed for the device as `vsProfiles`), each datasheet's through its VS Data unit in the frozen units map, and a roster's characteristic modifiers then change them as they did the catalogue's, so the builder, `list_units`, print, battles and the simulator read them alike. A unit profile takes the line named for it, else the one line VS Data prints for every model where the profile names one of the unit's models or the datasheet, else the line of the models the carrier rule reads its name as; a weapon profile takes the line of its wargear and mode in the same phase, spelled through the reviewed spellings, with a Hunter profile read as its Hunter mode. Profiles the catalogue prints differently that would take one line, as a Terminator with a storm shield beside one without, keep the catalogue's, and so do a characteristic VS Data leaves out or prints no roll for (a skill of 7), keywords holding rules words, and every Warhammer Legends and Crucible datasheet, as their prices do. Keywords are spelled as the release's keyword glossary names them, and one the catalogue links no rule for is explained by the rule or ability of its name; invulnerable saves and base sizes are read as above. The simulator finds a model whose profile the datasheet merged into an equal one by the raw profile's values, else by the one profile of its name, since the datasheet prints VS Data's. Earlier rules versions keep the catalogue's stat lines: their releases differ from it in hundreds of lines either way. `pnpm exec tsx scripts/vsDataProfileParity.ts [catalogue directory]` lists every difference per rules version, and `scripts/vsDataProfileCombat.ts` what the change does to the simulator's damage, defence and refusals for each datasheet and tournament list, both report-only into `data-dev`.
- The current rules version's attachments and transport capacities come from VS Data's `attachment` and `transport-profile` records the same way (`vsLinksIndex`, `src/shared/vsDataAttachments.ts`, in `vsProfiles`; the attachments are also the catalogue index's `attachments`, so a device judges them as the server does). VS Data decides every host it names, in either role and in any army, unless a catalogue keyword target admits it: its `conditional` entries become `AttachmentCondition`s that `inArmy` settles against the list's units, Detachments and the unit's own keywords, as Pactbound Zealots asks a Character and its unit to share a Mark of Chaos, and an unsettled attachment (reference pages, imports, the picker's joiners) admits every host some army allows, and a host not yet added is not refused for a shared keyword it may still take (`beforeHostChoices`). The catalogue's own reading (Leader text, associations, substitutions, keyword targets) adds only hosts VS Data never names, and stays whole for a datasheet VS Data has no record for, or whose record leads some units and supports others, so no pairing is lost; a condition no list can meet here (one on a faction) is left out with its hosts; its limits, required attachments and `requiresLeader` stay the catalogue's. A host is named as every catalogue datasheet of its VS Data unit is; a unit no catalogue datasheet stands for is left out, as no list can field it yet. A transport's VS Data capacity replaces what its printed rule reads as (`vsTransport`), except where VS Data records a capacity gap or a shape the printed form cannot hold (several alternative loads of several allowances, allowances wargear replaces), which keep the printed rule. `pnpm exec tsx scripts/vsDataAttachmentParity.ts [catalogue directory]`, report-only into `data-dev`, compares per book every datasheet's lead and support pairs and every transport's verdict on each datasheet of its book, before and after.
- Every rules version's lists are checked by that checker too (`vsDataErrors`, `src/shared/vsDataLegality.ts`), on each version's roster definitions and points (`vsRosterDefinitionsIn`), packed whole for the device: allies, exclusions, copies, unit and ally limits, sizes the player chose, Enhancements, Warlord, allegiances and Detachment tags, each datasheet read through the frozen maps with its Enhancement and allegiance options. Its problems replace the catalogue's copy limit on each datasheet VS Data checks, its keyword roster limits, the Game Datacards faction bans and the Enhancement count, while the catalogue's Detachment locks stay beside them until VS Data records Deathwatch's; the catalogue still checks each unit's wargear, the datasheets VS Data does not define, a Warhammer Legends or Crucible datasheet, or a Titan, that VS Data files under a faction the army neither is nor allies with (a fortification, an Aeldari Legends hero, a Crucible Deathwatch Agent the app's ally lists cannot name, or a chaos army's Titan, whose BSData ID it shares with the Imperial one VS Data reads it as; `vsDataChecks`), and a list VS Data cannot place: one of a faction with neither Detachments of its own nor `withoutDetachments`, or with a Detachment VS Data files under another faction. Any other list with no Detachment is told it needs one, as in the app. A faction with `withoutDetachments` (Titan Legions, Chaos Titan Legions) takes none: setup offers none, the list plays the faction's own dispositions (`vsDataWithoutDetachments`), and the checker refuses any it holds. A list none of whose book's datasheets reads as its faction's, as Titanicus Traitoris's read as the Imperial Titans they share BSData IDs with, stays with the catalogue's checks. The coverage report probes each datasheet under the first Detachment its faction lists, or none for a faction that takes none. An allegiance the builder offers a unit no option for is not asked of it, the Warlord is the unit's Character model where VS Data names one, and wargear an Enhancement needs is the catalogue's to check.
- A pick with `vs` (`VsPick`) is built from those definitions (`buildPick`, `src/shared/vsDataBuild.ts`) where VS Data defines its datasheet in the list's rules version, and from the catalogue otherwise, though a catalogue pick of a datasheet VS Data fields at sizes with gaps between them steps between those sizes: its size, models, wargear, model lines and keywords are VS Data's (`vsBuiltUnit`, `src/core/vsDataBuild.ts`, each selection on one model of its option's carrier, the largest group still holding what it replaces), and its price is `priceVsRoster`'s, copies counted across the list. Beside it `buildVsUnit` (`src/core/roster.ts`) builds the catalogue's tree at the same size with its Warlord, Enhancement and allegiance, and the pick's own catalogue choices where a translated pick keeps them: what still reads that tree (roster limits and keywords in the catalogue's checks, abilities, attachments, the simulator, the loadout search, the BattleScribe export) reads that until it reads VS Data's. `scripts/vsDataBuildParity.ts` builds every datasheet VS Data defines exactly both ways, from its default and from each choice the per-choice map gives, and compares price, models, wargear and keywords.
- A pick built by VS Data is that checker's whole: its models and wargear (`checkVsUnit`), its Enhancement, allegiance and Warlord, read from the unit VS Data fields (`VsBuiltUnit.unit`) with nothing read from catalogue choices. Its catalogue tree stays in the forces so the other picks' conditions still count it, but none of its nodes reports a limit, nor costs points where VS Data prices it (`evaluateForces`' `vsPicks`). Each Enhancement's first copy counts towards the battle size's limit, an Upgrade's included, and a copy past one, or past three of an Upgrade, is refused, as VS Data's checker does. In a list VS Data cannot place, the catalogue still checks its own entry's roster limits, and VS Data still checks its models and wargear (`vsPickErrors`). `pnpm exec tsx scripts/vsDataLegalityParity.ts [catalogue directory] [--list]` prices each exact datasheet's BSData default and each choice the options map translates as a one-unit list both ways and compares the verdicts.
- The builder offers a VS pick what VS Data offers it, in the shape it draws a catalogue unit (`vsUnitChoices`, `vsUnitToggles`, `vsModelKinds` in `src/core/unitChoices.ts`): a choice per open option, keyed by its roster-option ID with its wargear IDs as options, `models` where two or more kinds are counted freely, `enhancement` and `upgrade` for its one Enhancement slot, `allegiance`, and a Warlord toggle keyed by the model that holds it. The priced unit carries the unit's own records (`vsUnitRecords`), so `pickEditor` edits `vs` on the device with `vsWithChoice` and `vsResized`, and refuses an edit that leaves VS Data's checker more to find. `scripts/vsDataChoiceParity.ts` compares those offers with what the catalogue offers the same datasheet.
- What a book's lists may take is VS Data's too, through the same reading (`vsDataOffer`, `src/shared/vsDataOffers.ts`): the picker leaves out a datasheet VS Data's checker would refuse the army, as another faction's that no ally entry offers or one the faction excludes, and shows a datasheet as allied where VS Data files it under another faction, named as the catalogue names its source where the catalogue borrows it too. Setup, the reference pages and `list_factions` offer a book's Detachments but those VS Data refuses it, and none to a Titan army, Titanicus Traitoris's included (`offeredDetachments`), and each Detachment's force disposition is VS Data's, the catalogue's where it is one of VS Data's. The catalogue still decides what VS Data cannot place, and a book's datasheets and Detachments (`index.datasheets`, `detachmentsOf`) stay the catalogue's reach, which is what a saved or imported list resolves through, so a list keeps a unit or Detachment VS Data refuses: setup marks such a Detachment, and VS Data's checker refuses such a unit wherever it checks the list.
- `pnpm exec tsx scripts/vsDataParity.ts [catalogue directory] [construction directory] [list copy]` is the comparison gate, report-only, written to `data-dev/vs-data-parity.json`. For the current rules version it compares, per book, the datasheets the roster picker offers with the units VS Data admits to the faction, listed prices with VS Data's for each datasheet's smallest size, and each Detachment's force disposition. For every saved roster, list fielded into a battle and sealed-event entry in a local list copy (`pnpm exec tsx scripts/fetchProductionCopy.ts`, which keeps only the rosters, battle commands and sealed entries of a production copy in `data-dev/production-lists.ndjson.gz` and deletes the rest, or a `just rosters-fetch` snapshot), on the list's own rules version, it reads the list as a VS Data roster through the frozen maps, each unit's wargear as the fewest VS Data selections VS Data's checker accepts that give exactly the items Praetorium builds (`scripts/lib/vsDataRosters.ts`), then compares total and unit points and the verdict of the checks VS Data's replaces. Attachments, one Enhancement a unit, a saved datasheet, choice, unit size or Detachment that is gone, and the format rules stay Praetorium's and are left out of the verdict. The copy holds players' lists: keep it and the report in `data-dev`, report counts only, and delete the copy when done.

## Data

- Bump `CANONICAL_CATALOGUE_COMPILER_VERSION` when canonical records change, then republish via `catalogue.yml` with `force`.
- Parsed sources from `src/server/sharedJson.ts` are shared: copy before changing.
- Construction reads go in `constructionReads.ts` so the worker and server agree.
- Points come from each rules version's VS Data points (`vsPointsIn` in `src/server/vsDataPoints.ts`, `src/shared/vsDataPoints.ts`) for every datasheet whose VS Data unit has a definition there, joined through `catalogue/legacy-ids/` by the BSData IDs lists hold: unit cost rows, priced wargear, Enhancements and Detachment points, packed for the device beside the field manual. `mfmUnitFor` and `mfmDetachmentFor` read them first, so every price the builder, picker, datasheets and agents show follows; a VS Data cost row for one Detachment replaces the catalogue's price there, Detachment upgrades the catalogue adds included. Each earlier rules version prices from its own release, which reads the app build matching its field manual. A datasheet VS Data does not define is priced from the [MFM fork](https://github.com/richardsolomou/wh40k-11e-mfm) by name, and so is a Detachment VS Data does not price. Never duplicate prices in definitions.
- Imports read a list in any of the official app's languages through the names each rules version's VS Data release localises (`localisation/<language>.json`): compacting keeps every spelling of each faction, Detachment, Enhancement, force disposition, unit and the models and wargear under it, English first (`names`), every unit and Detachment by its VS Data ID. The rules a list is imported into carry them by the IDs saved rosters store (`importNames`), joined through `catalogue/legacy-ids/{units,detachments}.json`, and `loadCatalogueTranslations` adds them to the import translations. A datasheet or Detachment otherwise answers to the names BSData gave it, which New Recruit prints, frozen by stored ID in `catalogue/legacy-ids/{datasheet,detachment}-names.json`, an earlier rules version's under `<rules version>~<ID>` where they differ from the base's (`scripts/freezeImportNames.ts <catalogue directory>` adds a snapshot's and never removes one), not to the catalogue's own names.
- Community translations, including Portuguese and Russian, which the app does not print, come from [wh40k-11e-translations](https://github.com/richardsolomou/wh40k-11e-translations), a pinnable copy of nrdata.org, which serves only its live state; refresh it there with `bin/update` and a commit, never by fetching nrdata.org at build time. They are New Recruit's spellings keyed by BSData's English names, with no licence VS Data could publish them under, so they stay an import-only source here.
- `pnpm exec tsx scripts/importParity.ts record <file>` records what every import corpus list imports to; `compare <before> <after>` lists each that changed. A change to how imports read names keeps every list the same, or reads more of it.
- Definitions no longer update upstream. After a points update, dataslate or codex, run `just drift` and work its report (`data-dev/drift/drift.md`, JSON beside it): "likely edit" rows first, where Game Datacards and 40kdc-data agree against us, then "GDC differs" rows. Game Datacards is the authority; a 40kdc-only row is a lead to check against the cards, never an edit on its own. "New in GDC HEAD" shows what a Game Datacards bump would change.
- `changes/history.json` is immutable.

## Rules versions

- Saved lists carry `<edition-id>~<book-id>` and keep their version when the default changes. Never replace a retained edition with current rules or move its pinned commits.
- Promote a preview by keeping its ID and files and switching `status`/`default`; never rename or copy it.
- New MFM version: freeze the current base to explicit pins, add a new `base: true` default, and fold the outgoing base in `catalogue/edition-migrations.json`.
- Retired sources and IDs stay resolvable so old snapshots and rosters verify; retired IDs are illegal, never dropped or free.
- `scripts/retainRosterCatalogue.ts` is a manual release tool: it rebuilds a historical snapshot's profile construction with the compiler, transform, and icons pinned in `catalogue/retained-profile-build.json`, and packs the result as a new snapshot.

## Pricing and legality

- `evaluate.ts` reports unsupported semantics in `unhandled` and fails closed on unreadable conditions. Ability prose never applies benefits.
- `pointsBudget` changes only the points limit and strategic reserve limit.
- Never hide upstream disagreements from `just points` or lower its match rate.

## Top-four lists

- The Tournament lists tab's lists are fetched from 40k Stats and Mini Headquarters into `DATA_DIR/winning-lists` and imported on the web process in the background, paced between lists; never import them while answering a request.
- Every published placing is kept, with no date window: importing cleanly under the current revision is what removes a list built for removed datasheets or options. A list that imports but is no longer legal keeps its problem in its verdict and stays on the tab, marked; the builder's unit counts, grades and `list_winning_lists` by default read only lists legal today.
- A first import under a revision pauses after each list for four times as long as the list took, so the server keeps answering and the import takes about an hour; the tab shows the lists checked so far until it finishes, while the unit counts wait for the full set rather than marking units from part of it.
- Each list's verdict is kept per catalogue revision, and the draft its page reads per catalogue revision and app release, so a release that changes how lists import serves fresh drafts; changing what a verdict records must also change its stored shape, or old verdicts are served.

## Coverage bar

A release holds this bar, which only goes up:

- `just points` matches at least 99.9% of Munitorum prices and every faction file.
- Of the tournament lists in each of the `40kstats` and `lexmechanic` corpora exported from the official app's newest data, at least 95% import clean (`pnpm exec tsx scripts/importCorpus.ts run --source <source> --since 2026-06-20 --live`), and no change makes a clean list unclean.

## Saved IDs in VS Data

`catalogue/legacy-ids/{books,detachments,units,enhancements}.json` give the VS Data ID of each book, Detachment, datasheet and Enhancement ID a saved list can hold, and never lose a key: `scripts/freezeRosterIds.ts <catalogue directory> <unpacked releases, one directory per rules version>` adds what a new snapshot or release names and refuses to move a frozen ID. VS Data is the source of truth, so a datasheet's value follows the unit its rules version's release aliases it on (`bsdata.*`), or that unit's single replacement once retired; where a release moves an alias, the value is corrected in place, and `scripts/legacyIds.integration.test.ts` fails until it is. Read a list's IDs once its rules version is known (`currentRosterIds`): a key is `<rules version>~<ID>` where a retained rules version reads the ID otherwise, else the ID itself, and an Enhancement's key is `<VS Data Detachment>/<option ID>`, since one entry serves Detachments VS Data records apart. Books map by hand, Detachments and Enhancements by name within their faction with the script's reviewed spellings, datasheets by VS Data's `bsdata.*` aliases, else by exact name, and retired IDs through the retired-ID, migration and retained-version aliases. A retired unit with one current successor reads as the successor, and a chapter's book reads as `space-marines` in a release whose app build has no faction for that chapter. Where VS Data's unit requires an allegiance in every Detachment and a BSData datasheet already implies one, `units.json` also gives it under `allegiances`, by the same key, for a pick that holds no allegiance choice of its own: the one of the unit's allegiance choices the datasheet's name spells as whole words, as BSData's Khorne, Tzeentch, Nurgle and Slaanesh Soul Grinders are VS Data's one Soul Grinder, else the one the datasheet is built on before any choice is made, as Daemon Prince of Chaos starts on Khorne. A datasheet built with no allegiance, as Heretic Astartes Daemon Prince with no Mark of Chaos, implies none. A rules version's key falls back to the bare allegiance, so the freezer stops where a retained rules version implies none for a datasheet the current one gives one. Beyond new keys, that is the one way an entry grows: a frozen ID may gain an allegiance, never lose or change one. A VS Data alias names one unit, yet one Library datasheet can stand for different units by the book that links it, as the Library - Titans Warhound Titan is the Imperial one in an Imperial book and the Chaos Warhound Titan in a chaos book. So where a book's faction is offered neither the datasheet's unit nor that unit's faction, and exactly one unit an ally entry of the faction offers has a name ending in the unit's, `units.json` also keys the datasheet `<book>/<ID>` (`<rules version>~<book>/<ID>` where a retained rules version reads it otherwise, the datasheet's plain unit included), and `options.json` keys its choices alike. Every reader takes the book key first (`inBook`), with the list's book: a rules version's book key, the book key, a rules version's key, then the bare one.

A BSData rule, profile or entry finds its VS Data record by id, never by name, through `vsDataRecordOfBsdata` (`src/shared/vsData.ts`, read per rules version by `bsdataRecordsIn`): VS Data's `bsdata.*` alias of it, or, for a profile several datasheets carry that is a different record on each, or whose alias a datasheet contradicts, its entry in `catalogue/legacy-ids/bsdata-records.json`, keyed `<datasheet>/<id>` (`<rules version>~` first where a version reads it otherwise). The map holds only what an alias can't say, and only grows. An entry names a record reviewed as the same rule as the profile, never one found by name: the datasheet's own VS Data unit's record where one is, as for a unit's copy in another faction's catalogue, else a core rule's keyword record (`core-ability:`), and one its rules version summarizes (`scripts/legacyIds.integration.test.ts` checks that). A datasheet with no such record gets no entry. A reader keeps only an entry its rules version summarizes, since a bare key also reaches versions without that record.

`catalogue/legacy-ids/options.json` gives, for each datasheet entry of the current rules version, the VS Data selections each of its choices (`<choice key>|<option ID>`) stands for, or the `allegiance` it takes, with the selections that turn VS Data's first fielding of the unit into BSData's (`base`) and the options a floor pick's unmade choices take (`floor`); `legacyOptionsSchema` in `src/core/legacyIds.ts` says how a reader applies them. It reads the current rules version only, so never read it for a list of a retained rules version: freezing those under `<rules version>~<entry>` keys can come later, and until then each run lists the `~` entries and retired aliases it leaves out. Like the other maps it only grows: a mapped choice never changes, and a run that would change one stops. Beyond that growth, an entry changes only when `units.json` moves its datasheet to another unit, or when a `base` frozen as `unmatched` now maps: it is derived afresh, keeping every key it held, with those that no longer translate unmatched, and a moved datasheet whose new unit cannot be read takes `base: unmatched`, so none of its picks translate. A `floor` never changes, since it comes from BSData alone.

`scripts/freezeRosterOptions.ts <catalogue directory> <unpacked releases>` derives it from the catalogue alone. Each choice is built on the unit it is made on, its first fielding or, for a choice another opens, the unit with that one taken, and compared at the same size, so an option that brings a model is read against an ordinary model in its place. Every size and unit composition BSData fields is visited, and a key no visit reaches is listed as unmatched. A key maps to the fewest VS Data selections, up to four, whose wargear changes equal exactly what it changes, and may take back a selection VS Data's defaults, `base` or the choice above made. The selections come from the options of the VS Data model making the choice, and options no model carries. That model is the one named like the BSData model (its owner, or the option where the option is a model), else the one scoring best on shared words less words only its name has, leaving out the unit's name; where several tie or none is known, each candidate must give the same selections. Ties between selections go to option then wargear ID order, so the answer never depends on record order. Wargear compares by name through the script's reviewed spellings, leaving out only selections whose IDs are Enhancements.

VS Data's own checker (`checkVsUnit`) decides what may be mapped, at every size BSData fields the unit and VS Data can: a translation must raise nothing the unit without it does not, alone, in every pick of its divided group within its options' bounds, and beside each key of another choice read with it. Where the first translation fails, a later valid one is taken; a key with none, or one that fails beside another, is unmatched. `base` must be the same at every size, the only fewest selections that give it, and valid; otherwise, or where VS Data cannot field BSData's first size, it is `'unmatched'`. `floor` lists the option a floor pick's unmade choice takes where it is not the first fielding's.

`scripts/translateSavedPicks.ts [catalogue directory] [list copy]` reads the other way: each saved pick whole (saved rosters, lists fielded into a battle or a sealed event, and saved unit loadouts), in its own rules version, the way the switch will move them. It builds the unit as Praetorium does today. It then looks for the fewest VS Data selections whose unit has the same models and the same wargear through the reviewed spellings (`src/shared/wargearSpellings.ts`) and that VS Data's checker accepts at the pick's size; where none of the fewest is valid, it takes one part of the wargear a size larger. Option then wargear ID order only decides which answers the search keeps when there are more than 64 to a part or 4,096 to a unit; such a pick is ambiguous (`search-cap`), and the order never settles a tie. Equally few valid answers are told apart by BSData's own models: each kind of model must hold at least the copies of a disputed item that BSData's models of that kind carry, matched by the per-choice map's carrier rule (`src/shared/vsDataModelNames.ts`), and copies held outside any model, or on a model naming no single kind, may go anywhere. Each pick is `translated` (`fewest`, `longer-valid`, or `tie-placed` when the models settle a tie), `ambiguous` (`tie-placed-alike` or `tie-placed-elsewhere` when several or none remain, or `search-cap`), or `unmatched` (`no-unit`, `no-build`, `models-unread`, `models-refused`, `wargear-vs-data-lacks`, `no-equal-wargear`, `search-limit` or `refused-by-checker`). A pick of the current rules version is compared against how the per-choice map reads it. A pick holding an Enhancement and an upgrade, which a unit can't take together, is `unmatched` (`several-enhancements`), as is a loadout unit holding an allegiance, which a loadout doesn't keep by VS Data IDs. A unit needing an allegiance takes the one its choice names, else the one its datasheet stands for (`units.json`'s `allegiances`, as for one Soul Grinder datasheet per god); with neither, it is translated with none, so the builder asks for one, as the app does. A unit the catalogue's own checks refuse stays on BSData (`refused-today`), since VS Data accepting its translation would change what was saved. A Warlord is the unit's Character model, else its one model of a kind, as `vsDataErrors` reads it. Equipment VS Data's unit carries that no option of it takes away is the app's printed default, kept where BSData's built unit leaves it out (`defaults kept`), and a unit the pick's book can't field through its faction, parent or allies, as a shared library datasheet another faction's book reads as its own, stays on BSData (`not-in-book`). A translated pick that still puts an item on a different kind than the carrier rule reads BSData's models as using is marked `placed elsewhere`; the final freeze should review those, which mostly mark the rule's limits, as Thunderwolf Cavalry reading as all troopers. It writes the results to `data-dev/saved-pick-translations.ndjson` and the frozen translations (`savedPicksSchema`, `src/core/savedPicks.ts`) to `data-dev/saved-picks.json`: every translated pick's `VsPick` by `savedPickKey`, less any key two picks translate differently. Both are derived from players' lists, so they stay in `data-dev`.

`scripts/publishSavedPicks.ts [translator run]` publishes the run's translations in place of the published ones: that copy's keys alone go to the players' private bucket (`praetorium-private`) as `saved-picks/<sha256>.json`, and `src/shared/savedPicks.pin.json` pins that SHA-256 with `copiedAt`, when the copy's backup captured the database, just before its freeze, so everything saved before it is in the copy. The backup records that time in its manifest (`capturedAt`, `scripts/backupSpacetime.py`), the copy keeps it in its closing record, the translator refuses a copy without it and writes it, every live pick's key and the translations as one output (`data-dev/saved-picks.json`, `savedPicksRunSchema`) once that output reads whole, and the publish reads them from there, never from an argument. A key never changes meaning: a run stops before anything is written if a key both publications hold would read otherwise, or if a published key a live record of the copy still hashes to would leave (`nextSavedPicks`). A key that leaves only stops attaching, and its records read as their catalogue choices, so the last publication before BSData goes must hold every live pick that translates. A key the copy's picks read two ways is frozen for none and left out of that check, and the run lists it (`disputed`); the last publication must resolve or translate each of them. The file is strict (`savedPicksSchema`): a 16-hex key of a pick's content and the pick's VS Data IDs. It is derived from players' private lists (saved rosters, loadouts, fielded and sealed lists), so it is server-only: it lives in the players' private bucket (`praetorium-private`), a production server's `DATA_DIR/saved-picks/` and the operator's `data-dev`, and nothing serves it. Previews and CI on forks and Dependabot hold no key to that bucket; two same-repository CI jobs do, as `R2_*` (`ci.yml`'s `live-catalogue` and `catalogue.yml`), as they do for the bucket's other contents. A production server reads it from its data directory, else the bucket, verified against the pin (`savedPicks()` in `src/server/savedPicks.ts`). A translation attaches only to a roster, loadout or sealed-entry record saved before the pin's `copiedAt` and unchanged since, never to a battle read, which closes the oracle of saving a guessed pick to learn whether some list held it. It attaches only inside a read its authority already allows, to picks in that response, with a sealed entry's reveal state checked on every read, never for a key or pick a request names, and never as a map shipped to the device, which keeps only what it was given with a list. Until a server has it, and wherever it is absent, a pick reads as its catalogue choices. Run the translator on the newest production copy and publish again whenever more picks translate.

A pick's key hashes its rules version, its list's book and Detachments, and what decides how it builds (datasheet, allied book, size, choices, spreads, toggles, floor), never a nickname, note, attachment or transport, on the pick as `currentRosterIds` or `fieldedRosterIds` reads it. `withVsPicks` and `withVsLoadout` attach a pick's frozen `vs` on load without rewriting what is stored, and leave a pick that holds its own. A pick keeps its `vs` when it moves to another rules version (a conversion, a loadout used in another version, a folded version) or to another datasheet (a retired ID), and a changed Detachment drops only its Enhancement, as it drops the catalogue's. The list's reader checks it against its own rules version (`vsPickIn`, in `buildPick`): VS Data's `checkUpgrade` on the unit's `rosterRefs`, where every reference must be current there, and each model and option the unit's own. A pick that fails reads as its catalogue choices, as one saved before VS Data did. The runtime definitions hold current records only, so an aliased ID fails like a retired one.

`scripts/savedPickParity.ts [catalogue directory] [list copy] [translations]` is the gate: every list priced and checked as today and with its translated picks read as VS Data units, comparing each translated unit's points, model count, wargear and verdict (`checkVsUnit` against the catalogue's own checks of the unit), and each list's points; a list's verdict through VS Data's checker is the legality gate's. It writes the differing units to `data-dev/saved-pick-parity.ndjson`. The per-choice map stays for reading lists still spelled in BSData's IDs, as imports are.

## Roster migration

Before changing sources or saved-selection construction, baseline production rosters:

```sh
just rosters-fetch
just rosters-audit
cp data-dev/production-rosters.audit.json data-dev/production-rosters.baseline.json
just rosters-audit data-dev/production-rosters.json catalogue-data data-dev/production-rosters.baseline.json
```

Author replacements in `catalogue/roster-migrations.json` with a reason. Never fuzzy-match, substitute, or drop a selection, or suppress a legality error, to make the audit pass.

A choice a unit never made starts on the option its group names as the default (the one the card prints), whatever it costs; an optional group starts on named wargear. A unit marked `floor: true` builds each unmade choice at its cheapest option instead, the named default only settling a tie, as units were built before. `migrateStoredRoster` marks every unit of a row without `printedDefaults` and sets it, so the product data migration marks each older row once, and a save without `printedDefaults` is marked the same way: the client's `saveRoster` sends it with every save it makes or queues, and server code that saves a roster itself sets it, so a save an older app queued offline keeps its units' cheapest; `rosterFromRow` marks a row the migration has not reached yet. A battle's fielded list carries `printedDefaults` from `rosterSnapshot`, and folding one without it marks its picks. Never remove `floor` from a saved unit. A unit's listed price and the Munitorum point adjustment build at the floor too, so a costlier default is charged on top of the card's price.

Every catalogue publish (`pnpm catalogue:history`, against the published snapshot) and every live refresh (`prepareLiveRevision`, against the revision it follows) runs `checkIdDrops` (`scripts/lib/catalogueIdDrops.ts`) on the base rules. It fails when the new catalogue drops a book, datasheet, detachment, enhancement or option ID a saved roster can hold, and no map moves it, while:

- a new ID in the same scope carries the same or a near-identical name: a rename the maps must carry, even when the history reads it as a removal;
- or the data-update history does not record the removal of a book, datasheet, detachment or enhancement by that name.

An option that left its datasheet only reports. A failed refresh keeps serving the previous revision, so a release never publishes the drop. Map what saved rosters hold (run the audit above); `pnpm exec tsx scripts/catalogueIdDrops.ts <previous> <next>` runs the check on two catalogue directories, and with `--accept <reason>` records the rest in `catalogue/accepted-id-drops.json`.

## Privacy

- Who reads a roster, its notes, and its preparation follows the [privacy contract](../product-design.md#privacy-contract); exports never carry notes.
- Imports never silently drop or substitute units, and never overwrite an existing draft.
- Collection photos stay in the private bucket with location metadata stripped; every path that drops a photo row records it in `collection_photo_deletion` in the same transaction.

Before a catalogue release, run `just catalogue-preflight` against the proposed `catalogue.json`.
